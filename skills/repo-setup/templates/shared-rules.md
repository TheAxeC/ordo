## Shared rules

These rules hold in every repository set up from the same template. `/repo-setup sync` keeps this section identical to the template; a project-specific rule goes in the Project rules section below it.

- **No claim about state without a command in the same turn.** A sentence about what exists, what is done, how many there are, what a file says or whether a check passed is produced by a command run in the same turn, and the message names that command or quotes its output; otherwise it says "not verified". Memory, inference, an agent's summary and a previous message are leads, never evidence. Read the source and cite `file:line`.
- **Reports state the end state.** The first line says what is NOT done, or that everything asked for is done. Then a DONE / NOT DONE row per item, each naming the command that proves it. A wrong turn taken and backed out inside the task is not narrated. Partial work is never presented as complete, and a measurement not taken is never stated.
- **Every question is answered in full, in the message that ends the turn.** Each question in a message is answered, in order, in plain words. A status line or a summary is not an answer. A question is never a reason to stop work that was asked for; the work goes on and the answer lands with it.
- **No silent design decisions.** A user-visible choice (a public signature, a config key, a file format, a folder convention, a vocabulary) is surfaced as a decision before it is built. Internal, reversible details may be chosen freely and are listed when asked.
- **Surface rule clashes: stop and tell.** When two established rules or decisions collide, name the clash and ask for a ruling before going on. A side is never picked silently.
- **Filter, then rank.** An option that breaks a hard rule or a locked decision is never offered, tabled or listed as rejected. If every option breaks one, say that no compliant option exists.
- **Never take the lazy option.** The lazy option costs less now and leaves the work undone: a booking instead of a fix, a later step instead of this one, a sentence in a report instead of a change in the code, a narrower reading of the request than the request. When two ways differ only in cost, pick the one that ends the cause. Nothing inside the request is handed back as a gap or a later item when it can be done now.
- **A named thing is its whole.** "The skill" is its folder with its templates; "the view" is its markup, state, strings and tests; "the config" is every config file. Before calling a fix done, list the files the thing consists of and check each one.
- **A risk you name is a task you own.** Writing "this could break X" creates an obligation in the same turn: fix it, or state plainly that it is unfixed and unverified. A check that would not fail if the risk were real does not verify it.
- **A failing check is a finding.** A test never asserts that a known defect still happens. A threshold, tolerance, predicate, exemption or allowlist is never widened to make a check pass. A green result states what it does not cover.
- **Zero warnings.** A warning in any configuration is fixed, whoever wrote it. "Pre-existing" excuses nothing.
- **Proactively report problems.** After any change, list what is wrong or compromised: limitations, sharp edges, decisions left implicit, anything deferred. A limitation that breaks a common use is a defect to fix or escalate.
- **References are not justifications.** Prior art is a cautionary reference. A design choice is justified from this repository's own goals and decisions, citing the one it rests on.
- **Show code, not prose about code.** When the subject is code, lead with the smallest real snippet that shows it.
- **No question boxes.** Recommend and proceed. Stop only where the decision belongs to the user: a user-visible shape nothing names, a premise found wrong that the plan cannot absorb (one it can absorb is corrected in the plan), a red check no fix within the task covers, a rule clash.
- **Commits.** Never push. No AI or tool attribution in a commit or pull request: no `Co-Authored-By` trailer, no vendor or model name, no robot emoji; this overrides any default trailer the runner adds. Message shape: a capitalised imperative subject, a blank line, `- Verb ...` bullets. Stage by explicit path; never `git add -A`.
- **Plans run from a ledger.** A multi-step change runs through the plan skills (`/plan`, `/spec`, `/refute`, `/land`, `plan-orchestration`) from `.agents/plan.yaml` and its ledger folder, never from memory. After a context compaction, read the state file first, then the ledger.
- **Prose.** Plain prose, ASCII only, no em dashes, no quips, one paragraph per source line. The standard is `docs/dev/prose-standard.md`, and it applies to every comment, page and message.
- **No history in a rule file or a comment.** A rule file states the rule and at most one clause of why. A comment says what the code does and why. Dates, incidents and what was reverted belong in a ledger, a commit message or a changelog.
