## What to build

The goal's sentences, which the step is judged on, each to be carried by a numbered step of the skill:

- "The `research` mode of `researcher`, which takes an idea to results: the session directs the work through six named stages (Frame, Build, Baseline, Experiments, Compare, Consolidate), each with a completion criterion, and a stage can send the work back to itself or to an earlier one; each piece of code is built by a fresh agent from a written brief and read by a fresh reviewer before any job is submitted."
- "Frame sets the question, the baseline, the metric, the limits on storage and compute, and the dataset, chosen from candidates shown with their size, licence and fit to the limits."
- "Experiments holds one campaign or several, each with its own method. It runs the experiments, SLURM jobs among them, and when a result does not beat the baseline it diagnoses why (the dataset, the method, the implementation or the question) and proposes a new method, a change of the method or another dataset, never writing up a negative result; it stops after each such result or goes on by itself for a number of methods you set."
- "It states where a project's code, results, logs and drafts live, in a default layout whose entry file is the project's `README.md`, with dead ends kept runnable in `code/attic/`, and one project can hold several manuscripts."
- "An adopt mode reads a project already underway and continues from the first stage not done, counting partial or inadequate results as not done."
- "The `full` mode runs `idea`, then `research` and `manuscript`, shows the modes it will run and the ones it leaves out, as for a review paper or for results that exist, each with its reason, and goes on after you confirm."
- "The `research` mode holds a project to four rules: one documented command rebuilds every reported number, table and figure from the raw inputs, and names each missing prerequisite at its start; nothing computes on a cluster's login node, and every job goes through the scheduler; an idea is not shelved after a weak first attempt; and the project's notes let a new session resume without the conversation."
- The goal's `idea` sentence, which the step line's check reads with the others: "`idea` takes a rough sketch to research questions and claims: it works in rounds, each choice of the idea put with its options and a recommendation, runs `novelty` on each candidate claim between rounds, and writes the questions and claims into the project's `README.md`."
- The `idea` sentence that this step closes: `idea` "is reopened from Compare with the finding that changed the question" (ruling D26); `idea`'s side is landed (idea item 2, "the reopening evidence"), and Compare's side is built here.

2. `research`, the stages (rulings D7, D10, ADR 0053).
   - The session directs the work and builds nothing itself: it writes each brief, starts each builder and each reviewer, reads their reports, decides the next stage, writes the README and submits the jobs.
   - Six named stages in order, Frame, Build, Baseline, Experiments, Compare, Consolidate, each with a written completion criterion the session checks against the project's files before the next stage starts; the criteria stand in `references/research_stages.md`, one section per stage, each with what the stage does, what it leaves in the project, its criterion, and where it can send the work.
   - A stage can send the work back to itself or to an earlier stage, with the reason written in the README; Experiments holds one campaign or several, "trying out very different things", each with its own method and its own section in the README, a campaign able to loop within itself.
   - Each stage ends with the README updated (item 7) and the stage named that stands, so a new session resumes from the README alone.
3. Frame (rulings D11, D27, ADR 0053).
   - Frame sets the question and claims (from the README's `## Research questions and claims` when `idea` wrote it, or asked), the baseline, the metric, what counts as good enough, the limits on storage, compute, time and access, the cluster's facts (asked once and written to the README), the manual or automatic setting with its count of methods (item 5), and the dataset; the setting and its count stand in the README's section "constraints and limits".
   - The dataset: a lookup by the session (the web, and `lookup.py search` for the published works that report on a dataset) finds candidate datasets, each shown with its size, licence, how it is obtained, the published works that report on it and whether it fits the limits; the user picks, at a stop; the README records the choice and the reason. A Compare diagnosis that blames the dataset reopens the choice.
   - Each of these is a stop where the user's answer is needed, asked in one message where their prerequisites allow, each with options and a recommendation.
4. Build, Baseline and Experiments: builders and reviewers (rulings D10, D25, D11, ADR 0053).
   - Each piece of code is built by a fresh builder agent from a brief the session writes, in the form of a new page `references/research_brief.md`: what to build, the cases, the small local test, the files it writes, the rules of item 6 it is under. The builder reads its role page, a new page `agents/research_builder_agent.md`.
   - After the builder ends, a fresh reviewer agent that changes nothing reads the code against the brief, reruns the local test and looks for what makes a result false (a leak of test data, a wrong metric, a baseline run under other conditions, a seed or a split that differs); its role page is a new page `agents/research_reviewer_agent.md`. A finding goes back to a builder through a new brief; no job is submitted before the reviewer's report holds no finding that makes a result false.
   - No worktree, no landing, no ledger: the builder works in the project's `code/`, and the brief, the builder's report and the reviewer's report are files of `notes/`, linked from the README's section "the stage and campaign that stand".
   - The agents start on the runner's general-purpose agent with the runner's defaults, as the integrity agent does.
   - The small local test runs where the session runs only when that machine is not a cluster's login node (the cluster's facts of Frame say so); on a cluster it runs as a short job through the scheduler, as every other job does; the builder's and the reviewer's runs of it follow the same rule.
   - A piece of code goes back to a builder at most twice after its first review; a third review that still finds what makes a result false is the stop "A piece of code that does not pass its review", which shows the findings.
   - Jobs: the skill ships the rules for SLURM in a new page `references/slurm.md`, and no cluster's facts. The page holds at least: a job script per job in `code/hpc/`, submitted with `sbatch` from that folder; resource requests (time, memory, cores, GPUs) inside Frame's limits and the cluster's facts; output and error files in `logs/`, named by the job; arrays for a sweep and dependencies for a job that needs another's output; the job id read from `sbatch`'s output; `squeue` and `sacct` only when the user asks for polling; no work on a login node beyond editing, submitting and reading. Then: every job goes through the scheduler from a script in `code/hpc/`; nothing computes on a login node; after submitting, the session writes the job ids to the README's section "the stage and campaign that stand" and stops; it polls only when the user asks for it in the run, and stops polling when asked.
   - Baseline runs the baseline under the conditions of Frame; Experiments runs each campaign; each result is written to `code/results/` with the command that made it.
5. Compare (ruling D8, ADR 0053).
   - Compare reads each result against the baseline and against what Frame set as good enough.
   - A result that does not beat the baseline gets a diagnosis written to the README (or to a page of `notes/` it links): the cause named as the dataset, the method, the implementation or the question, with the evidence, and a proposal: a new method (a change of objective, optimisation or model structure), a change of the method, or another dataset. A dataset cause reopens Frame's choice of dataset; an implementation cause sends the work to Build, at most twice for one result before the stop of the manual setting shows it; a question cause reopens `idea` with the reopening evidence; a method cause sends the work to Experiments with the new method as a campaign.
   - The setting asked at Frame decides what follows, and the user can change it at any time in words: manual, the run stops after each such result at a stop that shows the diagnosis and the proposal; automatic, the run goes on by itself for the number of methods the user set, each with its diagnosis written, and stops when the baseline is beaten or the count is reached.
   - A result that does not beat the baseline is never written up as a result to publish: no text of the mode, and nothing it sends to `manuscript`, frames a negative or null result as a finding; it is guidance for the next method, recorded as a dead end (item 7).
   - An idea is not shelved after a weak first attempt: a stop or an end of the count shows what was tried and the next proposal; the mode never proposes to drop the idea after one method.
6. The four rules, each a bullet of Rules and each carried by the step that enforces it.
   - One documented command, `code/run_all.sh`, rebuilds every reported number, table and figure from the raw inputs, then runs `code/paper.py`, and names each missing prerequisite at its start before it does any work. `code/paper.py` builds every figure and table from `code/results/`. Build writes both and keeps them true as results are added.
   - Nothing computes on a cluster's login node, and every job goes through the scheduler (item 4, `references/slurm.md`).
   - An idea is not shelved after a weak first attempt (item 5).
   - The project's notes let a new session resume without the conversation (item 7).
7. The README and the layout (rulings D9, D28, D29, ADR 0053).
   - The default layout for a new project stands in a new page `references/project_layout.md`, exactly as ruling D29 gives it: `README.md` as the entry file with its sections (question and claims, constraints and limits, where things live, cluster facts, the stage and campaign that stand, results each with its file and command, dead ends each with why, papers, next); `code/` with `README.md`, `run_all.sh`, `paper.py`, `core/`, `experiments/`, `hpc/`, `data/`, `results/`, `figures/`, `attic/` (dead ends, each runnable, indexed in `attic/README.md`) and `.depositignore` (what stays out of a public deposit); `manuscript/`; `admin/`; `notes/`; `reviews/` for real reviews only, where no skill writes; `logs/`. A section of the README that grows too long moves to `notes/` and is linked. The page says that `## Research questions and claims` is the first section, the one `idea` writes.
   - `research` on an empty or missing folder makes the layout; on a project underway it moves nothing and records the project's own names in the README.
   - Every stage writes the README before it ends, so a new session resumes from it.
   - Dead ends: a method that did not beat the baseline is kept runnable in `code/attic/`, indexed in `attic/README.md`, and listed in the README with why it failed.
   - Several papers: the first in `manuscript/`, a further paper in `manuscript-<name>/`, the README's section "papers" listing the papers and the results each reports, code and results shared, `manuscript` and `integrity` run per paper; or, when the user asks, a further paper as a new project that copies the code it needs.
   - A further paper is written by `/researcher manuscript <project folder> --manuscript <name>`, a Quick start line of its own, which runs `/paper full '<project folder>' --manuscript '<name>'` (Open item I, C151); with no `--manuscript` the run is as it is.
   - `research` on a non-empty folder whose README records no stage of `research` is the stop "A project underway", which offers `/researcher research adopt <project folder>`.
8. Consolidate (rulings D12, D31, ADR 0053).
   - The one command is run once from the raw inputs in a clean copy of the project, through the scheduler on a cluster, and each number, table and figure it yields is compared with the reported one; a number is called reproduced only after that run, and a difference sends the work back to the stage that made it.
   - The clean copy is a copy of `code/` alone, made on the cluster's scratch storage named in the cluster's facts, or in a temporary folder off a cluster, that reads the raw inputs where they stand and copies none of them, so it stays inside Frame's storage limit. A difference sends the work back to the stage that made it; a second reproduction run that still differs is the stop "A number that does not reproduce".
   - Consolidate writes `experiment-record.yaml` in the project folder in the form of Schema 9 of `references/handoff_schemas.md`, each entry's `negative_results[]` filled from the dead ends of item 7 for that experiment, a list the integrity check holds claims against and that is never manuscript content, which `integrity` and `manuscript` read (SKILL.md "What it reads" 4); the integrity check's stop "The record of the experiments" then does not arise for a project `research` finished.
   - The completion criterion of Consolidate is the reproduction run's comparison with no difference, and the record written.
9. The adopt mode (ruling D30, ADR 0053).
   - It reads the README first and checks each stage the README calls done against that stage's completion criterion in the files; the first that fails is where it continues. Results that are partial, unfinished or below what Frame set count as not done.
   - With no usable README it reads the project against each stage in order, shows what it found per stage with the file that shows it, at a stop the user confirms once, writes the README sections and moves nothing.
   - A usable README is one that holds the section "the stage and campaign that stand"; the adopt mode writes the D29 sections a README lacks after its own sections and changes none of its own.
   - `research adopt` on a missing or empty folder is the refusal "Nothing to adopt", which names `/researcher research <project folder>`.
   - It then goes on as `research` from that stage.
