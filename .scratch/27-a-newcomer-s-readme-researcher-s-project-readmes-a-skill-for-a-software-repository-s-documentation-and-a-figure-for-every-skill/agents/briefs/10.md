## What to build

1. **The deposit list.** In `references/project_layout.md`, "The deposit", the four folder lines of what a run makes or holds are written anchored, `/data/`, `/attic/`, `/results/` and `/figures/`, so each names the folder beside `.depositignore` and no folder deeper down. Every other line stays as it is: `secrets/`, a cache, a compiled file or a secret file is left out at any depth, since a secret below the top must stay out of a public deposit. The bullets under the list spell the four folders as the list does, and one of them says in one sentence why those four carry the leading `/`.
2. **Adding to a `.depositignore` that exists.** The rule is written once, in `project_layout.md`, "The deposit", in place of line 108; readme item 3 of `SKILL.md` (line 447) names that section for it and states no rule of its own. The rule:
   - The draft keeps every line of the file, in its order, comments and blank lines included.
   - A line of the list is added when the file does not already have it. A comment or a blank line has nothing.
   - A folder line of the list (`/data/` and the three others) is had when a line of the file that does not start with `!`, read without a leading `/` and without a trailing `/`, `/*` or `/**`, is that folder's name. So `data/`, `/data/`, `data` and `results/*` have the folder, and `data/raw/`, `/data/*.csv`, `**/data/`, `src/data/` and `!data/README.md` do not.
   - Any other line of the list is had when the file holds that exact line.
   - The lines added are placed together, under one comment line, above the file's first line that starts with `!`, or at the end when it has none, so no added line overrides a re-include of the file.
   - The draft shows each line it adds and, for each line of the list it does not add, the line of the file that has it.
   - A made-up example, built from no real project, stands beside the rule: a `.depositignore` holding `results/*` and `!results/model.pt` gets `/data/`, `/attic/` and `/figures/` above `!results/model.pt` and no `/results/` line.

## Decisions taken in this brief (each reversible, none silent)

1. The rule for "had" in item 2 is equality after stripping, and a `!` line never has a folder. Run on five real files read in step 8's runs:
   - engram `/data/`: stripped `data`: had. Output: no data line.
   - linfoot `results/*`: stripped `results`: had. `!results/batch1/`: a `!` line: has nothing. Output: no results line.
   - linfoot `attic/`: had. Output: no attic line.
   - linfoot, no line on `data` or `figures`: Output: `/data/` and `/figures/` added above the first `!` line.
   - linfoot `*.py[cod]` against the list's `*.pyc`: not the exact line: `*.pyc` added, which leaves out nothing the file does not already leave out.
2. `secrets/` stays unanchored, so a secret folder at any depth stays out of a public deposit; ADR 0057's "secrets" holds for every depth.
3. The checks run in a copy of the working tree in the scratch folder, so the repository's configuration, its ignore files and its uncommitted changes apply as they do in the repository, and nothing of the repository is written before the approval.
4. Lint commands run beside format commands, since a linter rejects the copied `utils/figures.py` of a Python repository as a formatter does.
5. `untested` stands between `works` and `partial`, in the order of how much a user can rely on the capability.
6. The record of item 5 is a new ADR that refines 0058, under `docs/dev/change-standard.md` rule 5, rather than a change to 0058's Decision.
