## What to build

1. **`skills/code/handbook/SKILL.md`**, a new skill in the layout of `docs/dev/skill-layout.md`, every section of "Sections, in order" in its order, `metadata.version: "1.0.0"`.
   - The frontmatter `name: handbook`. The `description` says what the skill does and what it leaves behind, in one paragraph, then `Triggers on:` with at least one phrase per case it is for (write a software repository's README, write the documentation of a repository, a getting-started guide, a manual, reference pages, a feature map, diagrams of a repository, a one-page manual, update a repository's docs, and phrasings of these), at most 1,024 characters by the command of `docs/dev/skill-layout.md`, "Frontmatter". It names no neighbouring skill.
   - `## Quick start` holds a code block, closed before the next `## ` heading, with each invocation and a short comment: at least `/handbook [<repository folder>]`, the whole run, the repository the current folder when none is named. A narrower invocation (one kind, or the README alone) is added only when "Steps" gives it its own path.
   - `## Use instead` names, each with its situation: `researcher`'s `readme` mode for a research project's README; `ordo-init` for setting a repository up for the plan skills (which writes a short README of its own in a new repository); `codebase-design` for standards pages of the code; `code-comments` for comments in the code.
2. **The kinds**, as ADR 0058 decides, written from a fixed set, each with its path as D34 rules: a page that exists stays at its path; a new page goes to its kind's path.

   | Kind | New path |
   |---|---|
   | the README | `README.md` |
   | a getting-started guide | `docs/user/guides/` |
   | manual pages, one per part of the product | `docs/user/manual/` |
   | reference pages, one per public surface | `docs/user/reference/` |
   | a feature map, each capability with its status | `docs/user/feature-map/` |
   | diagrams, each a graph in a Python file with its `.svg` | `docs/user/diagrams/` |
   | a one-page `manual.html` built by a script | `docs/user/manual.html` |
   | the API pages from the doc comments, by the language's own tool | as "Decisions taken in this brief" 4 gives |
   | an index of the documentation | `docs/README.md` |

   - The skill states what each kind holds, and when a repository has a use for it, in a reference page `references/kinds.md` (material a step reads in some runs, `docs/dev/skill-layout.md`, "Writing for an agent"), with the README's core as item 4 gives it.
3. **The first stop**, before any page is drafted: the kinds the repository gets, each with its path (the existing page's path, or the new path of item 2), and each kind left out with its reason, for the user to confirm or change. When the run would copy the engine, the skill reads `python3 --version` first, and a version below 3.10 is named at this stop as a question (the version the engine needs, and that the diagrams kind is left out until the user's `python3` has it). Nothing is drafted or written before the user confirms. The skill reads the repository's code and existing documentation before this stop, enough to name each kind's pages (which parts of the product, which public surfaces).
4. **The README's core**, as ADR 0058 and D26 decide: `# <name>` with its opening paragraph, what it looks like, build and run or install, where to look, and the license. The repository's own sections are kept and brought up to date, each fact kept. The skill states the core's order and that a section of the repository's own is placed where it reads best around the core, which the draft shows.
5. **Each page drafted from the code and the existing documentation**, each claim with its source file named in the draft; a page that exists is brought up to date with every fact of it kept, the draft showing where each fact of the old page went; what no file holds is a question in the draft. Every page is shown as a draft and written only after the user's approval: a stop that shows each draft whole, with every change from the file it replaces, and writes the drafts the user approves, a draft the user corrects shown again.
6. **The diagrams**, as ADR 0060 decides: the skill copies `templates/figures.py` into the documented repository as `utils/figures.py`, writes the repository's diagrams as graphs in a Python file beside it (as "Decisions taken in this brief" 2 gives), runs that file with `python3`, and the drafts show each `.svg` it wrote under `docs/user/diagrams/` and its graph file.
   - A `utils/figures.py` that exists and equals the template is kept; one that differs is not written over and is shown at the first stop as a question (keep it, or replace it with the template).
   - A `utils/diagrams.py` that exists is a page that exists (item 5): its draft keeps every graph of it, each change marked, and it is never written over unseen.
   - The diagram file finds the repository root from its own path (`__file__`), so `python3 utils/diagrams.py` writes under `docs/user/diagrams/` of the repository from any working directory.
   - Each label is written into the diagram file as a Python string literal by `repr`, so a quote or a backslash in a label runs and draws as given.
   - A diagram the engine refuses (`FigureError`: a label that does not fit, a non-ASCII label, a cycle not marked as a return) has its error shown and its graph corrected in the draft, at most three tries per diagram; a diagram still refused after the third is left out, and the drafts stop shows it with the engine's error for the user.
7. **The `manual.html` script**, as D35 rules: `skills/code/handbook/templates/manual.py`, a Python standard-library script, with no test, that the skill copies into the documented repository as `utils/manual.py` and runs with `python3` to build `docs/user/manual.html`: one HTML page with a tab per document, each document a Markdown page of the repository's documentation that the kinds of the run hold, converted to HTML by the script.
   - Its head comment says what it does, how it is run, the Python version it needs, what it reads, what it writes, each error it raises and every exit status it returns (change standard rule 14), in the shape of the engine's head comment. It runs on Python 3.9 or later, so the macOS system `python3` runs it.
   - It reads the documents it is given (as "Decisions taken in this brief" 3 gives) and writes `docs/user/manual.html`, creating `docs/user/` when it does not exist; it reads back what it wrote and, when the text read back differs, removes the page and exits non-zero naming it (change standard rule 16).
   - Each tab's label is the document's path relative to the root, and its id is that path with each character outside `[a-z0-9]` written as `-`, so `README.md` and `docs/README.md` get two tabs that differ.
   - A relative image or link path is rewritten relative to `docs/user/manual.html` from the folder of the document that holds it, and a link to another document of the run points at that document's tab, so a README's images under `docs/figures/` show in the page.
   - A link or image target whose scheme is not `http`, `https` or `mailto`, such as `javascript:`, is written as text and not as a link; every target is escaped inside its attribute.
   - A raw HTML line outside a code block, such as `<p align="center">`, is escaped and shown as text.
   - No document given is a usage error (exit 2, nothing written); a root that is not a directory, a document that does not exist and a document that is not UTF-8 each exit non-zero naming the path, and nothing is written. An absolute document path inside the root is accepted.
   - Every text it puts into the page is escaped for HTML, so a `<`, a `&` or a quote in a document reaches the page as text (change standard rule 15).
   - A document path that resolves outside the repository is refused, and so is a document that is not UTF-8.
   - The page it writes is ASCII where its documents are ASCII, carries its own styles inline, loads nothing from the network, and reads the same in a light or a dark browser theme.
   - A `utils/manual.py` that exists in the documented repository and differs from the template is not written over and is shown at the first stop as a question, as item 6 says for the engine.
8. **`docs/dev/scripts.md`**: a row for `skills/code/handbook/templates/manual.py` under "User scripts" with its job; the engine's row says that `handbook` copies the engine into a documented repository's `utils/` beside the two figure scripts that import it.

## Decisions taken in this brief (each reversible, none silent)

1. `handbook` runs in the user's session and starts no agent: each page is drafted by the session from the code and the documents it reads. ADR 0058 names no agent, and a run is the user's reading of every draft.
2. The diagrams of a documented repository stand in one file `utils/diagrams.py` beside `utils/figures.py`, one function per diagram that returns its graph, written in the way `docs/figures/gen_figures.py` uses the engine, and writing each `.svg` to `docs/user/diagrams/<name>.svg` with `write_figures`. One file keeps every diagram's source in one place to diff, as `gen_figures.py` does for Ordo.
3. `manual.py` takes the repository root and the documents as arguments, in the order of the tabs: `python3 utils/manual.py <repository root> <document> ...`, each document a path relative to the root. The skill writes the command with the run's documents into `docs/README.md`, so the user rebuilds the page with the same command. It converts the Markdown that the kinds' pages hold: headings, paragraphs, bulleted and numbered lists, tables, fenced code blocks, inline code, bold, italic, links and images; any other line is written as a paragraph of text.
4. The API pages are built by the language's own tool (such as Doxygen for C or C++, TypeDoc for TypeScript, pdoc for Python, rustdoc for Rust): the skill writes the tool's configuration with the output folder `docs/user/reference/api/`, names the build command in `docs/README.md`, and runs the command when the tool is installed. With the tool not installed, the first stop names the tool and its install command, and the kind is left out of the run with that reason. The generated pages are build output, which the skill does not commit or write into the drafts.
5. After the user's approval the skill commits every file it wrote in the run in one commit, by explicit path, rather than the `.svg` alone: ADR 0060 decides that it commits the `.svg` it draws, and the `.svg` without the graph file and the engine that draw it, or without the pages that show it, is a commit that cannot be rebuilt or read.
