## What to build

When the step is done, a lookup is never refused for a rate limit that this machine's own requests cause, a 429 that names a wait over 60 s costs one request per index and not three retries per call, and the same index request of the four index commands is sent once in 30 days. Every command prints what it prints now for every reply it gets; only the reasons named below are new.

### 1. Each index host paced across processes

- `arxiv_turn`'s mechanism is generalised to a turn per host: before each request to a paced host, the process holds an exclusive `flock` on its lock file in `tempfile.gettempdir()`, waits until that host's gap has passed since the time the file holds, makes the request, and writes the time the request ended.
  - A redirect counts as a request of the host it goes to, and takes that host's turn.
  - The behaviour on a file that cannot be opened, locked or read, or holds text other than a time (the full gap), and on an empty file (no wait), is `arxiv_turn`'s.
  - `arxiv_turn` stays a module-level function that `once` calls for the arXiv hosts, since the existing arXiv-turn case patches `lookup.arxiv_turn`.
- The paced hosts, their names, lock files and gaps (Decision 1):

  | Host | Name | Lock file | Gap |
  |---|---|---|---|
  | `api.crossref.org` | `crossref` | `ordo-lookup-crossref` | 1.0 s, or 0.35 s when `CROSSREF_POLITE_EMAIL` is set |
  | `api.openalex.org` | `openalex` | `ordo-lookup-openalex` | 1.05 s, or 0.21 s when `OPENALEX_API_KEY` is set |
  | `api.semanticscholar.org` | `semanticscholar` | `ordo-lookup-semanticscholar` | 1.05 s |
  | `arxiv.org`, `export.arxiv.org`, `www.arxiv.org` | `arxiv` | `ordo-lookup-arxiv`, as now | 3.0 s, as now |

- Every other host (`doi.org`, a publisher's site, an open-access URL) is not paced.
- The wait of a 429 retry (item 2) runs after the lock is released; the retry takes a new turn.

### 2. A 429 handled by what it says

- `Retry-After` is read as follows:
  - a whole number of seconds from 0 to 60: that many seconds, a value below 1 waiting 1 second;
  - an HTTP date: the seconds from now to that date, rounded up, a date with no zone read as GMT, a date in the past waiting 1 second;
  - a whole number or a date more than 60 seconds ahead: no wait, item 2's long case;
  - absent, or any other text (a fraction such as `2.5`, a negative number, a word): no value, the 2, 4, 8 schedule.
- A 429 with a value of 60 seconds or less is retried after that many seconds, at most 3 times. After the third retry the index is left out with the reason "HTTP 429 after 3 retries", as now.
- A 429 with no value is retried after 2, then 4, then 8 seconds, and then left out with "HTTP 429 after 3 retries".
- A 429 whose value is more than 60 seconds is not retried. The request is left out at once with the reason "HTTP 429, retry after <n> s", `<n>` the seconds of `Retry-After`, rounded up.
  - From an API host (`api.crossref.org`, `api.openalex.org`, `api.semanticscholar.org`, `export.arxiv.org`), the process also writes the time of the reset, now plus `<n>` with `<n>` capped at 86400, to that host's skip file in `tempfile.gettempdir()`.
  - From any other host, no skip file is written.
- The skip file is `ordo-lookup-skip-<name>`, `<name>` from the table of item 1, with `-key` appended when that host's credential is set (`CROSSREF_POLITE_EMAIL` for Crossref, `OPENALEX_API_KEY` for OpenAlex, `S2_API_KEY` for Semantic Scholar), since a budget is per key. arXiv has no credential.
  - It is written to a unique temporary file in the same folder (`tempfile.mkstemp`), mode 600, and moved into place with `os.replace`, so a reader sees a whole time or no file.
- Before any request to an API host whose reply is not in the cache (item 3), a process reads that host's skip file. While the time it holds is in the future, no request is sent, and the request is left out with the reason "HTTP 429, retry after <n> s", `<n>` the whole seconds left, rounded up. A file that cannot be read or holds text other than a time is ignored. The skip never applies to `arxiv.org` or `www.arxiv.org`, the pages `check-urls` and `fetch` ask for.
- `Reply` carries the reason of a 429, so every place that prints a left-out reason or a status reason prints the true one: `resolve`, `search`, `refs`, `cited-by`, `bibtex` (`lookup.py:1252`), the title check of `check-urls`, and `fetch` (`lookup.py:1385`). `check-urls` prints its status 429 for a key's URL as now; for a URL whose request a skip prevented, it prints the reason of the skip as a URL that gave no answer.

### 3. Index replies cached on disk (choice C111)

- The cache is on only for the commands `resolve` (`resolve --entry` included), `search`, `refs` and `cited-by`. `Client` gets a flag that turns it on, off by default, and `main` sets it for those four commands. `bibtex` (its `lookup_arxiv` path included), `check-urls` (its title check included) and `fetch` neither read nor write the cache. `StubClient` and `RecordingClient` have no cache, so every existing case prints what it prints now.
- With the cache on, each reply that `get_parsed` receives with status 200 for a URL on `api.crossref.org`, `api.openalex.org`, `api.semanticscholar.org` or `export.arxiv.org` (the host of the URL `get_parsed` receives), and that its parser parses, is stored. A 200 that parses to "not found" (a search with no result, an arXiv feed with no entry) is stored too. A later `get_parsed` of the same URL, from any process with the cache on, within 30 days of the store, returns the parse of the stored body and sends no request.
- Nothing else is stored: no reply other than 200, no body that does not parse, no URL of another host, and no request made by `client.get` outside `get_parsed`.
- The folder is `$XDG_CACHE_HOME/ordo-lookup` when `XDG_CACHE_HOME` is an absolute path, else `~/.cache/ordo-lookup` (a relative or empty `XDG_CACHE_HOME` is ignored), created with mode 700.
- Each entry is one file named by the SHA-256 hex digest of the URL, holding the URL, the time stored and the body, mode 600. It is written to a unique temporary file in the folder (`tempfile.mkstemp`, a name no entry can have) and moved into place with `os.replace`, so no process reads half an entry; a temporary file is never read as an entry.
- An entry is used only when its URL equals the request's and it is less than 30 days old; an older entry is replaced by the new reply.
- Once per process, at its first store, the folder is pruned: entries older than 30 days and temporary files older than 1 day are removed.
- The key and the entry hold no credential: the URL is the one `get_parsed` receives, before `prepare`.
- A folder that cannot be made or written, or an entry that cannot be read or parsed, is treated as no entry: the request is sent and the command prints what it prints now, with no error line.

## Decisions taken in this brief (each reversible, none silent)

1. The gaps. Each gap keeps within the strictest per-second limit the host states for the requests `lookup.py` sends:
   - Crossref 1.0 s for the public pool (its reply said 1 a second, below its page's 5) and 0.35 s for the polite pool (its reply said 3 a second, below its page's 10);
   - OpenAlex 1.05 s with no key and 0.21 s with one, since `search` sends queries with more than 5 operators (1 and 5 a second);
   - Semantic Scholar 1.05 s: 1 a second with a key, and with no key a share of a pool of 1000 a second that every caller in the world draws on, where one request a second from this machine is the most it can count on.
   - The gap runs from the end of one request to the start of the next, as arXiv's does, which keeps one request at a time per host on the machine.
2. 60 seconds as the line between waiting and leaving out: a wait longer than that holds an agent while its context costs usage, and OpenAlex's spent budget answered 4356 s.
3. The skip file per API host and per credential in the temporary folder, beside the lock files, so every process sharing the folder learns of a long wait from one reply; capped at 86400 s, since no index has stated a longer one.
4. The reason "HTTP 429, retry after <n> s", which states only what the reply says, since a long `Retry-After` from Crossref or Semantic Scholar is not known to be a spent budget.
5. The cache at the `get_parsed` level, keyed by the URL, which holds no credential there; 30 days as C111 took it; on only for the four index commands, as C111 (a) excludes `check-urls` and `fetch`, and `bibtex`'s arXiv path with them, since `bibtex` writes an entry from the reply it gets now.
6. The cache folder under an absolute `XDG_CACHE_HOME`, else `~/.cache`, the place a command-line tool's cache goes on Linux and macOS alike.
7. A retry's wait outside the host's lock, so a long wait holds no other process; each retry takes a new turn.
