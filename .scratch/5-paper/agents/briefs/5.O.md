## What to build

### 1. The strategist writes no script and starts no agent (ruling item 1)

- In `SKILL.md` "Agent prompts", the rule that the agent starts no agent and the rule that the agent writes no script and runs none of its own apply to every role, the literature strategist included. Every start of the strategist is bound by both: a theme run, a merge job, the merge run, the synthesis start and the single strategist (the terms of What to build 4).
- The strategist runs, besides the `lookup.py` commands of What to build 2:
  - `curl` to save a work's own page into its folder of the temporary folder;
  - command lines of `grep`, `sed -n`, `awk`, `sort`, `uniq`, `comm`, `cut`, `tr` and `wc` over its own files;
  - a shell redirect (`>`) of a command's output into a file of its folder of the temporary folder.
- It writes no file of code and runs no interpreter of its own: no `python3 -c`, no heredoc script, no `.sh` file.
- The session makes each start's own folder of the temporary folder with `mktemp -d` inside the run's temporary folder and names its absolute path in the start's prompt. A start writes no file outside the run folder and that folder, and nothing under `/tmp` outside `$TMPDIR`, as ADR 0020 decides.
- The strategist page's "The boundary of its work" states both rules and the list of commands for the agent itself.
- The session of a lit-review run writes no script either. Each command it runs is one its items name.
- `SKILL.md` "Anti-patterns" gains a row: a script, a file of code or an agent of a start of the strategist's own; why it fails (what the script wrote is no reading of a source, and nothing in the run's records shows the judgment); what to do instead (the `lookup.py` command, the agent's own edits, the session's start).

### 2. Every index query through lookup.py (ruling item 2, with the premise correction)

The rules of the search say, each as its own bullet:

- Every query to the interface of an index is made with `lookup.py`. The indexes are Crossref, OpenAlex, Semantic Scholar, arXiv, PubMed E-utilities, Europe PMC and DBLP.
- WebSearch finds sources and venue pages.
- WebFetch reads, or `curl` saves, a work's own page: its landing page, its arXiv abstract page or its proceedings page. The page serves the annotation and the entry.
- `curl` never queries an index's interface.
- A database `lookup.py` does not query (IEEE Xplore, ACM DL, Scopus, Google Scholar, Connected Papers, and every other of the page's Step 2 table) is searched by WebSearch alone, or named "not reached" with the reason.
- The strategist runs no `lookup.py bibtex`, as ADR 0040 decides; it writes each entry from the record it read.

The strategist page changes to match: Layer 2 runs `refs`, Layer 3 runs `cited-by` in place of "Google Scholar / Scopus "Cited by"", Layer 4 runs `search` in place of "Semantic Scholar / Connected Papers", and the Step 2 table and "Edge cases" say how a database `lookup.py` does not query is reached.

The rule on the User-Agent changes: a request the agent sends itself with WebFetch or `curl` carries a generic User-Agent and no personal name or email; `lookup.py` sends `CROSSREF_POLITE_EMAIL` to Crossref only when the user set it.

`skills/paper/templates/lookup.py` gains these commands, each in its head comment (the usage line with each identifier kind spelled out, as the existing lines do; the command's bullet; what it reads; what it prints; its errors; its exit status), on the Python standard library alone:

- `refs <DOI | arXiv ID | PMID | OpenAlex ID | Semantic Scholar ID> ...`: for each input, a line naming it, then one record line per work it cites. The records come from OpenAlex's `referenced_works`, asked in batches of 50 with the `openalex_batch` route of 8624025. An input OpenAlex does not hold, or holds with an empty `referenced_works`, takes Semantic Scholar's references, and a PMID takes Europe PMC's references; the line says which index gave the list, and an empty list from every index prints "no references listed" with each index's reason, never a bare zero.
- `cited-by <DOI | arXiv ID | PMID | OpenAlex ID | Semantic Scholar ID> ... [--since <year>]`: the works that cite each input, from OpenAlex's `cites:` filter, then Semantic Scholar's citations, and for a PMID Europe PMC's citations. `--since` keeps works of that year and later; Semantic Scholar's list is filtered after it is read, since its interface takes no year.
- Both commands read every page up to 1000 works per input and print the total the index gives. A list cut at 1000 prints "cut at 1000 of <total>".
- `resolve <DOI | arXiv ID> <DOI | arXiv ID> ...`: several DOIs or arXiv IDs in one call. Each block is opened by a line naming the identifier and holds the lines `resolve` prints for it alone today, in the order of the arguments. OpenAlex is asked in batches of 50 (`doi:` and `ids.arxiv:` filters), Crossref in batches by its `doi` filter, arXiv by `id_list`, and Semantic Scholar per identifier. An argument read as a title among several is an error block of its own ("error: <argument> is not a DOI or an arXiv ID"), and the other blocks are printed. A single title takes one call of its own, as today.
- `index-abstract <DOI | arXiv ID | PMID:<n>> ... --into <folder>`: for each identifier, the abstract from the first index that gives one, in the order OpenAlex, Semantic Scholar, Crossref, Europe PMC, PubMed, arXiv. It writes `<folder>/<stem>.abstract.txt`, `<stem>` made from the identifier by `file_stem`. A PubMed abstract of several labelled parts keeps every part in order with its label, and the tags of a Crossref JATS or a Europe PMC abstract are taken out. It prints one line per identifier: the index it came from, or that no index gave one with each index's reason. An existing `<stem>.abstract.txt` is refused for that identifier, as `text` refuses. Its replies are not stored in the reply cache, as `fetch`'s are not.
- `dblp <title> ...`: the DBLP records of each title from DBLP's publication search, each hit with a title ratio of 0.70 or more printed with its venue, year, pages, type and DBLP key, a CoRR record marked as such. A reply that does not parse leaves DBLP out with the existing reason "HTTP <status>, the body does not parse".
- `search` also queries PubMed (E-utilities `esearch`, then `esummary`), at most 20 records, merged with the other indexes' records on a shared DOI as the existing merge does.
- E-utilities, Europe PMC and DBLP are paced hosts with the lock files `ordo-lookup-pubmed`, `ordo-lookup-europepmc` and `ordo-lookup-dblp` and the gaps of Decisions 3. They are API hosts for the 429 handling, with the skip files `ordo-lookup-skip-pubmed`, `ordo-lookup-skip-europepmc` and `ordo-lookup-skip-dblp`, each in the head comment's lists.
- The replies of `refs`, `cited-by`, `dblp`, the batch requests of `resolve` and PubMed's part of `search` are stored in the reply cache as those of `resolve` and `search` are, keyed by URL. A request that is not a GET is not stored.
- An identifier with a character a URL or a filter reads (`;`, `<`, `>`, `#`, `(`, `)`, `|`, `,`) is percent-encoded in every request it reaches, and matched exactly.
- An index left out part-way through a batch (a long 429 that writes its skip file) prints "<index>: left out, <reason>" in each later block, and the other indexes go on.
- The exit status of each new command is stated in the head comment's "Exit status", by the existing rule: 0 when it ran and found nothing to fail; 1 when an input got no record, no list or no abstract from any index; 2 for a call it cannot read.
- Every output stays plain text for a person, one line per record, never JSON.

Where the skill uses them:

- The theme runs, the merge jobs, the merge run and the single strategist run `search`, `refs`, `cited-by`, `resolve`, `index-abstract`, `dblp`, `fetch` and `text` themselves. `SKILL.md`'s table of each role's `lookup.py` commands gives them to the literature strategist.
- Lit-review item 2's identifier check runs `resolve` once for each file, with every identifier of the file as its arguments, and item 4 the same over `refs.bib`.
- The parallel starts share each paced host's lock file in the run's temporary folder, so their requests to one host take turns. The prompts say so, and that a batch command asks once for many works.

### 3. Entries and prose written by the agent (ruling item 3)

- The prompts of a literature search and the strategist page say: the agent writes each `.bib` entry and each sentence of its report files itself, with the Write and Edit tools, from what it read. No script writes, assembles, generates or patches a report or a `.bib`.
- Each start keeps a screening file in the run folder, `screening-<name>.md` (`<name>` as Decisions 2 gives it): one line per record screened, with its stage, its decision and its reason. The agent writes the lines itself.
- Each count in a report comes from a command over the agent's own files: a screening count over its screening file, a matrix count over the literature matrix of the report, a gate's number over the report's sections.
- The agent writes each count with its command and the command's output into `counts-<name>.md` in the run folder. A count is never typed in or changed by hand.

### 4. Only the session starts agents; the merge stage in parallel (ruling item 4)

The terms, each with a glossary entry (What to build 8):

- **merge job**: a start of the literature strategist the session makes after the theme runs, for one job of the merge stage.
- **merge run**: the start that removes the duplicates and writes the merged report, as it does today, without the jobs that move to the merge jobs.
- **synthesis start**: the start that writes the section "Synthesis Analysis" in lit-review mode.
- **citation round**: one backward round and one forward round of citation chaining, run as two merge jobs at once.

Steps 8's theme search and "The prompts of a literature search", with two search themes or more:

1. The theme runs run as today, all at once. Each theme run's report names the core set it chained from.
2. When every theme run has ended and has been read (and sent back where its report shows work undone), the session starts these merge jobs at once:
   - one per theme run whose hand-on list is not empty, assessing the leads and the other sources it hands on, a list of more than 40 sources split into jobs of at most 40;
   - where a theme run reports its citation loop open, the first citation round: a backward job over the union of the core sets the theme runs name, and a forward job over the same set for the last three years;
   - one job searching the intersections of the search themes that the research question joins, and the venues the topic needs.
3. Each merge job reads and annotates each source it includes. It writes `review-<name>.md`, `refs-<name>.bib`, `screening-<name>.md` and `counts-<name>.md` in the run folder, under the theme run's rules on search, requests, downloads, annotations, preprints, `.bib` entries and final message.
4. In lit-review mode the session runs the identifier check (lit-review item 2) on each `refs-<name>.bib`.
5. The citation rounds go on as What to build 7 says.
6. The session then starts the merge run, fresh. It is given `config.md`, every theme run's and merge job's files, in lit-review mode `checks.md`, the sources given and, where the mode's item gives one, the `.bib` with its manifest. It removes the duplicates and writes the merged annotated bibliography, the literature matrix, the gaps, the skew advisory, the recommended sources, the excluded and dropped sources, the screening results, the quality gates and the report of the citation rounds. It writes `review.md`, `refs.bib`, `screening-merge.md`, `counts-merge.md`, the files of "Reading a given source list" for a given list, and, where a manifest is given, the patch with the mode's id.
7. Where a quality gate fails, its failure handling's search is one more merge job the session starts; the merge run is then resumed with that job's files.
8. In lit-review mode the session then starts the synthesis start, fresh, given `config.md`, `review.md`, `refs.bib` and `counts-merge.md`. It writes the section "Synthesis Analysis" into `review.md` by its own edits.
9. The send-back of a merge run whose report shows work undone applies to each merge job, the merge run and the synthesis start: each is resumed once with that work named.

- Every rule of the merge run at the base is carried to the start that now does its work, its conditions kept; none is dropped.
- Every later input for the strategist goes to the merge run, which holds `review.md` and `refs.bib`, except an issue in the section "Synthesis Analysis", which goes to the synthesis start. Lit-review items 4 and 7 name the start they send each item to.
- The single strategist (one search theme) does every job itself, What to build 1, 2, 3, 5, 6 and 7 binding it.
- No start of the strategist starts an agent.

### 5. Small contexts (ruling item 5)

Every literature-search prompt says, each as its own bullet:

- The output of `search`, `refs`, `cited-by`, `resolve` over many identifiers and `dblp` is written to a file of the start's folder of the temporary folder, and the agent reads the lines it needs with `grep` or `sed -n`.
- A full text from `fetch` or `text` is read in the parts the annotation needs, from the file the command names in its output.
- A report file of another start is read by its sections.

### 6. The send-back rules in the first prompt (ruling item 6)

Each theme run's prompt, each merge job's prompt and the single strategist's prompt carry, from the first start, the work whose absence the session sends back:

- the five kinds of work of Steps 8's send-back of a theme run (a source that passes every gate held back; records excluded by a rule its page does not hold; records a query returned and the run did not retrieve; a citation loop left open for want of a round; a period of recent work not searched);
- no source excluded because a lookup failed and not on what the source says: such a source is looked up by `resolve`, `index-abstract`, `dblp`, its DOI's landing page and its venue's page before it is excluded;
- every annotation complete under the headings of the strategist page's annotation format;
- each sub-topic's minimum, or the documented search showing fewer exist.

### 7. The citation loop closes (ruling item 7)

- The strategist page's stopping rules: the search stops when at least 3 of the conditions hold and condition 4 is among them.
- With two search themes or more, after each citation round the session reads the two jobs' reports. Where a round included a cited work not yet collected, the session starts the next round over the works that round included, both jobs at once.
- The rounds end when a round includes no cited work not yet collected: condition 4 holds.
- The rounds are counted, at most 8. A loop still open after the eighth round is the stop "The citation loop does not close" of `SKILL.md` "Stops": it shows the works not collected and the rounds run; the options are another 8 rounds, or the run going on with those works named in the report and the final message. Under the instruction not to stop it takes another 8 rounds once, then goes on with the works named. The stop gets its row in the Stops table and its name in the line "Stops this mode can reach" of full, outline-only and lit-review.
- The single strategist runs its rounds the same way.
- The report says whether the citation loop closes and after how many rounds.
- The page's "When none of the 5 holds after 4 rounds of search, the agent records "search limitation"" stays for the other conditions; the change to it is reported (change-standard rule 17).
