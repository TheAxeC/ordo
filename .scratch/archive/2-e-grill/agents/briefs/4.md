## What to build

Both pages are templates `repo-setup` copies into a repository and adapts to its names (step 7). A place the repository fills in is written as `<...>`, the form `templates/CLAUDE.md` uses. No project name appears in either page, and no name of a library or tool of the source repositories (cathedra, rite, curia, monastery, game-engine, missal, oculus, cockpit, research-hub, Ordo): the skills carry no project name (`README.md`, first paragraph; the change standard's "Rules this repository already states").

Each principle and convention is written in short sentences joined by full stops, not semicolons, as the prose standard's section B limits semicolons in running prose. The check that enforces a rule is named inside the rule's own sentence where the repository has one (for example "checked by `<the size check>`"), never as a trailing field repeated on every bullet, which the prose standard's section 0 forbids as a repeated construction.

1. `skills/repo-setup/templates/docs/dev/design-principles.md`, independent of language:
   - Title `# Design principles`.
   - The opening paragraph: the sentence of ruling O2, verbatim: "A design ruling decides what is built. It never exempts the code: every line is written to the standards pages, so that people can read, use and maintain it." Then: a principle without a concrete form is a slogan; the concrete form below is the rule, and a check enforces it where one exists.
   - One bullet per principle, each **bold name** then its concrete form in general terms, drawn from the three sources:
     - Single responsibility: one module owns one subject; a class keeps one invariant; a file holds one subject; a member reaches another subject's state through that subject's interface, never through a copy.
     - Separation of concerns, high cohesion, low coupling: the code is layered and a layer sees only the layers below it (`<the layers, top down>`); a module reaches only what its build declaration grants; a public interface names no third-party type; a forwarder (a member whose whole body is a call to the same member elsewhere) is deleted.
     - Open for extension, closed for modification: a new case (a view, a backend, a key, a command) is added by registering it at an extension point the code exposes (a registry, an interface), never by editing the code that consumes it.
     - Substitutability: every implementation of an interface honours the whole contract; no member is defaulted to a silent no-op; a refusal goes through the error type, never through a flag that means two things.
     - Interface segregation: one small interface per subject; a caller depends on the interface it uses; a member no production caller uses is not on an interface.
     - Dependency inversion: a module depends on the interface a lower layer declares, never on a concrete type of a higher one; collaborators are passed in explicitly as a context parameter, a constructor argument or a function parameter.
     - No globals: no singleton, no global logger, no `getInstance()`, no module-level or static mutable state; an exception is an ADR the maintainer rules on, never a precedent.
     - Do not repeat yourself: one body per rule; a computation written twice is folded to one home; a table the build can derive is generated; a rule in prose is stated once and cited elsewhere (the comment rule, for one, is in `coding-standards/common.md`).
     - Keep it simple: the plain shape first (a value type over a builder, a function over a template, a direct call over an indirect one where the callee is known); a mechanism is justified from the repository's own goals (`<the goals>`), never from what another project does.
     - You are not going to need it: nothing is added for a caller that does not exist; a member, parameter, option or file whose only user is a test is deleted with its test; a public member exists because a caller calls it, and it is documented where that caller reads; a future need is a roadmap entry, not code.
   - After the bullets, one paragraph: a principle a check of the repository enforces names that check (`<the checks>`); a principle without one is checked by reading at review.
   - Length: every principle in at most five short sentences, the page under 60 lines.
2. `skills/repo-setup/templates/docs/dev/coding-standards/common.md`, the conventions that hold in every language:
   - Title `# Coding standards: every language`, and one opening sentence saying the language pages beside it add to it and never repeat it.
   - One bullet each, the check named in the rule's sentence where one applies:
     - File size: a source file stays under `<1000>` lines, checked at `<900>`; a file approaching it is split by subject, never by line count.
     - Folder size: at most `<ten>` items in a source, test or tool folder.
     - Formatting: one formatter, its configuration pinned in the repository, run by a command in the verify list; a failing format check is fixed by running the formatter, never by hand.
     - Comments: a comment says why, never what the code already says; no history in code or comments (no date, no step or item number, no "was", no "used to").
     - Character set: ASCII only in every authored file, except where a file's format requires otherwise.
     - Markdown and YAML: one continuous line per paragraph and per bullet; no hard wrapping.
     - Names: a name says what the thing is in the repository's vocabulary (`docs/glossary.md` where it has one); one thing has one name everywhere.
     - Errors: a failure is reported through the language's error mechanism with what failed and why; nothing fails silently, and no catch-all hides a failure.
     - Tests: a test proves behaviour whose failure costs something, and fails on the tree without the change.
   - Length: under 40 lines.
