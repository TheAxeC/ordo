# Brief: 1, a committed runner for a plan's verify list

Read `docs/dev/change-standard.md` first; its rules govern this step unchanged. Then, in full: `docs/dev/skill-layout.md` and `skills/repo-setup/templates/docs/dev/prose-standard.md`.

## What is on the tree (read on main at 73c188a)

- A plan's verify list is the `verify:` key of the first fenced `yaml` block of its `orchestrator-state.md`: a YAML list of command strings, one of them written as a folded scalar (`- >-` followed by the indented ASCII check). Checked: `sed -n 5,20p .scratch/2-b-repair-what-the-audit-of-plans-1-2-and-2-a-found/orchestrator-state.md`.
- The list holds nine test commands of the form `sh <path>.test.sh 2>&1 | tail -1`, then `python3 utils/check_skill_layout.py`, then the ASCII check. Checked: the same command.
- `docs/dev/building.md:19` says a test passes when it exits 0 and its last line starts with `PASS:`, and that the filter keeping the summary line is `2>&1 | tail -1`. With that filter, a shell's exit status is `tail`'s, so a red test piped through it exits 0: `sh -c 'printf "FAIL: x\n"; exit 1' 2>&1 | tail -1; echo $?` prints `FAIL: x` then `0`.
- No committed script runs a verify list: `ls utils` prints `check_coverage.py check_coverage.test.sh check_rule_inventory.py check_rule_inventory.test.sh check_skill_layout.py check_skill_layout.test.sh pin.sh pin.test.sh`.
- PyYAML is already a dependency of the checks: `utils/check_skill_layout.py:33` imports `yaml`; `python3 -c "import yaml; print(yaml.__version__)"` prints `6.0.3`.
- The test lists that name every test: `README.md:105-113` (code block) with one bullet per test at `README.md:116-124`; `docs/dev/building.md:6-14`; `docs/dev/change-standard.md:42-50`. `docs/dev/building.md:25` says a new script under `utils/` adds its test to both the README and that page.
- Test conventions, from `utils/pin.test.sh:1-15`: a head comment naming the cases, `set -u`, a `fail()` that prints `FAIL: <what>` to stderr and exits 1, a scratch folder from `mktemp -d "${TMPDIR:-/tmp}/<name>.XXXXXX"` removed by a trap, and a last line `PASS: <script> scratch tests`.

## What to build

1. `utils/verify.sh`, a POSIX `sh` script, invoked as `sh utils/verify.sh <state file>` from the repository root.
   - It reads the `verify:` list of the state file's first `yaml` block through `python3` and PyYAML (a short embedded Python program that prints the commands NUL-separated, or one per line with the folded scalar joined as YAML joins it).
   - For each command in order:
     - When the command ends with the filter ` 2>&1 | tail -1`, it runs the command without the filter (`sh -c '<command>'`, stdout and stderr captured together to a file under a scratch folder), and the command passes only when its exit status is 0 and its output's last line starts with `PASS:`. It prints that last line.
     - Any other command runs as written and passes only when its exit status is 0. It prints the command's whole output.
     - A failing command prints `RED: <command>`, its exit status, and its whole captured output, and the runner stops there with exit 1.
   - After the last command it prints `verify: <n> commands passed` and exits 0.
   - A missing or unreadable state file, a state file with no `yaml` block, or a block with no `verify:` list prints a message naming what is missing and exits 64.
   - Every command runs from the directory the runner was started in, which is the repository root of the checkout it checks (the worktree or main).
2. `utils/verify.test.sh`, in the conventions above. Its cases, each on a scratch state file and scratch test scripts:
   - all green: a filtered passing test, an unfiltered passing command and a folded-scalar command; exit 0, the `PASS:` line and the unfiltered output printed, then `verify: 3 commands passed`;
   - a filtered test that prints `PASS: x` as its last line but exits 1: red;
   - a filtered test that exits 0 but whose last line is not `PASS:`: red;
   - an unfiltered command that exits 1: red, its output printed;
   - the runner stops at the first red command: a command after it does not run (it would write a marker file that must not exist);
   - a missing state file, a state file with no `yaml` block, and a block with no `verify:` key: each exits 64 with its message.
3. `README.md`: `sh utils/verify.test.sh` in the Tests code block after `sh utils/pin.test.sh`, and a bullet after the `pin.test.sh` bullet saying what the test checks. A paragraph (after the layout-check paragraph of the Tests section, or where the section describes running the checks) says that `sh utils/verify.sh <state file>` runs a plan's verify list and why it exists: a filter hides a test's exit status, and the runner checks both the exit status and the `PASS:` line.
4. `docs/dev/building.md`: `sh utils/verify.test.sh` in the command list after `sh utils/pin.test.sh`, its comment in the list's style; and a sentence after line 19 saying that `sh utils/verify.sh <state file>` runs a plan's verify list, passing a test only on exit status 0 and a `PASS:` last line, and that a landing books the lines it prints.
5. `docs/dev/change-standard.md`: `sh utils/verify.test.sh 2>&1 | tail -1` in the command list after `sh utils/pin.test.sh 2>&1 | tail -1`; and a sentence after the list saying that a step's verification is run with `sh utils/verify.sh <state file>` and that a report quotes the lines it printed, never a count.

## Decisions taken in this brief (each reversible, none silent)

1. The runner is a `sh` script with an embedded `python3` program for the YAML, since the plan names `utils/verify.sh` and PyYAML is already required by the layout check.
2. The filter is recognised only as the exact suffix ` 2>&1 | tail -1`, the one form the pages use; any other command is judged on its exit status alone.
3. The runner stops at the first red command, as `docs/dev/change-standard.md:55` has a red test rerun without its filter and read before anything else.

## Conventions

- ASCII only, no history in any comment or page, the head comment of each script saying what it does and why.
- Script lines about 100 characters at most; a paragraph or bullet is one source line in Markdown.
- The prose standard applies to every new sentence: plain, active where the actor matters, no repeated construction, sentences of about 20 words unless the mechanism needs more.
