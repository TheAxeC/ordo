## What to build

1. **Every list item of the ten `skills/*/SKILL.md`, read one by one.** Each item outside a code fence and outside a table is read in full, the 707 items the count finds and any item the count misses. For each, the builder decides whether it holds two or more requirements that can each be broken while the others hold.
   - Such an item is split into one item per requirement, as Decisions 1 and 2 say.
   - Every item that holds one requirement stays as it is, byte for byte.
2. **What stays joined.** These are one requirement and stay in one item, whatever joins them:
   - a qualifier that changes the rule: an exception, a limit, a condition, a default;
   - a list inside one requirement, such as a semicolon-separated list of the kinds of a finding, or "Show, in this order: a; b; c";
   - an explanation of the rule: a "since", "so" or "because" clause, or a second sentence that gives the reason or points at where the rule is stated in full;
   - a definition that the rule then uses;
   - the items of a list whose entries each end in a semicolon, such as `skills/refute/SKILL.md` lines 66 and 91 and `skills/spec/SKILL.md` line 165;
   - two actions that are one act and cannot be done apart.
3. **Meaning kept.** Each split keeps the rule's meaning and scope, as rule 17 of `docs/dev/change-standard.md` says: every condition, exception and limit of the old text is kept with the requirement it governs, and none is added. A qualifier that governs both requirements is repeated in both, or the subject it names is repeated, so each new item reads alone. Words are moved, not rewritten: the new items use the old item's words, with only the joining word or punctuation removed and a subject repeated where a new sentence needs one.
4. **Position references kept.** After the splits, every position reference of the kinds listed in "What is on the tree" points at the item holding the same rule it pointed at before. A reference whose target moved is updated in the same step. The report lists each reference before and after, with the rule text it points at.
5. **The report** lists every item split, and a sample of the items kept with the reason each stays, as "Report" says.

## Decisions taken in this brief (each reversible, none silent)

1. **A numbered item keeps its number.** A numbered item that holds two requirements keeps its first requirement as its text, and each other requirement becomes a sub-bullet under it, indented as the file's other sub-bullets are. No numbered item is added or removed, so every `Steps <n>` and `"What it reads" <n>` reference keeps its target. An existing sub-bullet that holds two requirements is split into sibling sub-bullets.
2. **An unordered bullet splits into sibling bullets.** A bullet of an unordered list, a Rules bullet included, splits into bullets at the same level, in the old order. A `Rules <n>` reference whose target moves is updated (What to build 4).
3. **Tables and code blocks are out of scope.** `docs/dev/skill-layout.md` line 45 governs bullets and items. A table cell is governed by line 48 ("A cell holds a phrase or a sentence"), which ruling GG does not name.
4. **Only the ten `SKILL.md` files.** Line 3 of the layout page names `skills/<name>/SKILL.md`, and ruling GG names the ten skills' `SKILL.md` files. The templates under `skills/*/templates/` are files a skill copies into a repository and are not under the layout page.
