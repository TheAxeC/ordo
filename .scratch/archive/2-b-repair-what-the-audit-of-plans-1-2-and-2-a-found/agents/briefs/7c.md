## What is on the tree (read on main at 01b029e)

- `skills/plan-orchestration/templates/launch.sh` has 806 lines (`wc -l`). The runner's `guard` sub (lines 379-403) forks the guard, which checks its process group (line 388) and then waits with `Time::HiRes::sleep(0.1) while kill 0, $watch;` (line 399) before it writes the builder's code. `kill 0` succeeds on a zombie. So a killed session leader that its parent does not reap keeps the guard waiting, holding the launch's lock, and no exit file is written. Checked with `grep -n 'kill 0\|getpgrp' launch.sh`.
- The launch refuses a pid file that names a live process with `kill -0 "$old_pid"` (line 744, `grep -n 'kill -0'`). A zombie leader passes that check and refuses the relaunch.
- `$detach` (lines 444-473) forks the session leader and exits once the leader has written its pid, so the leader's parent is then the system's init process (launchd on macOS), which reaps it. A leader stays a zombie only when its parent is alive and does not reap it, for example under a Linux child subreaper that does not reap.
- The texts that read a pid as gone when `kill -0` fails: `skills/plan-orchestration/SKILL.md` line 106 (the resumption check) and line 194 (item 5 of the launch); `skills/land/SKILL.md` Steps item 1 (lines 39-44), which requires "a shell builder's pid must then be gone". The guard's texts: `launch.sh` head comment lines 39-47 and the runner's comment lines 221-228, `SKILL.md` lines 183 and 216, `templates/launch-note.md` line 31. Checked with `grep -n 'guard\|kill -0'` on each file.
- `skills/plan-orchestration/templates/launch.test.sh` has 1662 lines. Its `not_alive` (line 301) is `! kill -0`, used by `expect_gone`, `run` (line 345) and `land_wait`. `session_gone` finds a session's processes through `os.getsid` over `ps -ax`. `patched <name> <perl expression>` makes a changed copy of `launch.sh` (line 278).

## What to build

1. **One meaning of "gone" for the session leader.** A pid is gone when `kill -0` fails or when `ps -o stat= -p <pid>` shows a state starting with `Z`. The guard uses it: it checks `kill 0` every tenth of a second as now, and while `kill 0` succeeds it asks `ps` at most once a second, so a leader left as a zombie is counted gone within about a second. The launch's refusal of a pid file naming a live process uses it too, so a zombie leader does not refuse a relaunch.
2. **The texts made true.** `launch.sh`'s head comment and runner comment, `skills/plan-orchestration/SKILL.md` lines 106, 183, 194 and 216, `templates/launch-note.md` line 31, and `skills/land/SKILL.md` Steps item 1 say what the code does: a pid counts as gone when `kill -0` fails or `ps` shows it a zombie, and a KILL to a leader its parent does not reap still leaves the exit file.
3. **The test helpers.** `not_alive` in `launch.test.sh` counts a zombie as gone, as the land skill does.

## Decisions taken in this brief (each reversible, none silent)

1. Zombies are found with `ps -o stat=`, which macOS and Linux both have, rather than `/proc`, which macOS lacks. `ps` is run only while `kill 0` succeeds, and at most once a second, so a normal end starts no `ps`.
2. The case keeps a killed leader a zombie with a patched copy of `launch.sh` in which the process that forks the leader stays alive without reaping it for a bounded time (for example an intermediate process between `$detach`'s parent and the leader that sleeps a few seconds after the fork and then exits), so the launch still returns once the pid file is written.
