# Brief: 18a, `land.sh` lands a step that has no commit to copy

Read `docs/dev/change-standard.md` first; its rules govern this step unchanged. Then, in full: `docs/dev/skill-layout.md` and `skills/repo-setup/templates/docs/dev/prose-standard.md`.

## What is on the tree (read on main at ce253cb)

- `skills/land/templates/land.sh` is 467 lines (`wc -l`). After the worktree's add and wip commit (lines 342 to 363) and its checkout of `<pkg>-land` from main (lines 365 to 368), line 371 runs `git cherry-pick "$landing_base..$landing_pkg"` in the worktree, and line 391 runs `git cherry-pick -n "main..$landing_pkg-land"` on main. The verify list runs after that, at line 398 (`grep -n "cherry-pick\|verify list" skills/land/templates/land.sh`).
- When the range holds no commit, `git cherry-pick` prints `error: empty commit set passed` and `fatal: cherry-pick failed` and exits 128. Checked with git 2.49.0 on a scratch repository: `git cherry-pick main..x` and `git cherry-pick -n main..x` with `x` at main's head both exit 128 with those lines.
- So a step whose builder wrote only ledger files (which the add at line 343 leaves out) and made no commit has an empty range `<base>..<pkg>`. Line 371 fails, no conflicting path is listed, and the script exits 128 at line 380 without running the verify list. Plan 2.B's step 18 met this at its landing.
- `skills/land/templates/land.test.sh` is 952 lines. Its header comment (lines 2 to 24) lists the cases it covers; none is a landing with an empty range (`grep -n "empty\|no commit" skills/land/templates/land.test.sh` prints no such case). It builds ledgers with `make_ledger` (line 93); the red-list case at lines 539 to 561 shows how a red verify list is asserted (`RED:` line, exit 1).
- `skills/land/SKILL.md` Steps 4 (line 55) says the landing runs `git cherry-pick -n <base>..<step>` on main, and "The landing script" (lines 118 to 145) says what `land.sh` does; neither says what happens when the range is empty.
- The ledger's `land.sh` and `land.test.sh` are byte-identical to the templates (`cmp` prints nothing for both).

## What to build

1. `skills/land/templates/land.sh`: after the worktree's checkout of `<pkg>-land`, count the commits of `<base>..<pkg>` in the worktree (`git rev-list --count`). When the count is 0, print one line to standard output, `nothing to copy: <base>..<pkg> holds no commit`, with the two values filled in, skip both cherry-picks (line 371 and line 391), and go on to the verify list and the booking as before. A failed count (git exits non-zero) fails the landing with git's output and its exit status, as every other git step does. When the count is above 0 nothing changes.
2. The head comment of `land.sh` gains one sentence saying that a range with no commit copies nothing and the landing still runs the verify list.
3. `skills/land/templates/land.test.sh`: the two cases below, each in its own scratch repository with a worktree at the base and no commit after it, and the header comment's list of cases extended to name them.
4. `skills/land/SKILL.md`: under Steps 4, a sub-bullet saying that a range with no commit, as when the step's only output is a ledger file, copies nothing and the landing goes on to Steps 6; under "The landing script", a bullet saying the same of `land.sh`. Each bullet holds one requirement, as `docs/dev/skill-layout.md` line 45 requires.

## Cases

1. Must pass. A worktree at the base whose builder made no commit and left only an untracked file under the ledger root; a ledger whose verify list passes. `land.sh <pkg> <base>` exits 0, prints `nothing to copy: <base>..<pkg> holds no commit`, prints `verify: <n> commands passed`, prints the `=== booking ===` block, and afterwards `git diff --cached --name-only` on main prints nothing and main's copy of the ledger file is unchanged. On the unchanged tree it exits 128 with `error: empty commit set passed`.
2. Must refuse. The same worktree, with a ledger whose verify list holds a red command. `land.sh` exits 1 and prints verify.sh's `RED:` line for that command; main has nothing staged. On the unchanged tree it exits 128 with `error: empty commit set passed` and no `RED:` line.
3. Must pass, unchanged. The existing clean landing (one committed file, one pending file) still copies both files onto main: its staged paths are `committed.txt` and `pending.txt`, and the new line `nothing to copy` does not appear in its output.

The builder's first task, before any code changes: turn every case above into a test of the step, run the tests against the unchanged tree, and note each case's result. No prototype script stands in for the tests.

When the first run finds a case the brief's own rules get wrong, the builder stops there, before changing any code, and hands back the first run and that case, with the rule and the result it gives. The orchestrator rules on the case and resumes the builder with the ruling, and the final report carries it.

## Decisions taken in this brief (each reversible, none silent)

1. The count is taken after the checkout of `<pkg>-land`, so the branch exists in both paths and the resume logic of the preflight (lines 299 to 337) is unchanged.
2. The line printed is `nothing to copy: <base>..<pkg> holds no commit`. It goes to standard output, as the other progress lines do (`worktree git commit: nothing staged, no wip commit made`).
3. Only the empty range is handled. A range whose commits are all already on main (so the cherry-pick onto `<pkg>-land` would make empty commits) is not part of this step.
