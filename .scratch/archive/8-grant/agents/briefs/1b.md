## What to build

Seven changes to `skills/academic/grant/`, then the gaps of text. The plan's ruling "What the first run showed" names them. Each item states what must hold; the builder words the skill's text, in the skill layout and the prose standard.

### 1. The compile's engine

1. Steps 9 names the engine itself, and no longer takes the engine of the `paper` skill's Steps 11. The engine is the first of these that applies:
   - the engine a `% !TEX program =` line of the main `.tex` names;
   - the engine that wrote the log beside the application's own PDF, `<main>.log` in the folder of the main `.tex`, read from the log's first line (`This is pdfTeX`, `This is XeTeX`, `This is LuaHBTeX` or `This is LuaTeX`);
   - XeLaTeX, when the main `.tex` or a file it brings in loads `fontspec`, `unicode-math` or `polyglossia`, and LuaLaTeX when it loads `luacode` or holds `\directlua`;
   - pdfLaTeX otherwise.
2. The session finds the engine with `grep`, writes the engine and the rule that gave it into `checks.md`, and names both in the message that ends the run, with the sentence that a `% !TEX program =` line in the main `.tex` fixes the engine.
3. The flags are `-pdf`, `-xelatex` and `-lualatex`, with `-interaction=nonstopmode -halt-on-error` and the main file name.
4. Every compile of the run takes the same engine, and `draft` item 10 says that the compile the `paper` skill's format-convert makes for a `.docx` takes it too.
5. The formatter's direction says that it sets the layout only with what the run's engine compiles, so that a font is never set with a package of another engine.

### 2. The page count before the draft

1. In `draft`, when `main.tex` exists and the funder config's row `(whole document)` has a limit in pages, the session compiles the application before the structure architect is started (Steps 9, the compile alone, in `compile-0/`), and reads the page count of the log.
   - A compile that fails is written into `checks.md`, and the run goes on with the page count "not known: the application did not compile before the draft".
   - On a runner without `latexmk` the count is "not known: no `latexmk`".
2. The session adds two rows to `config.md`, as it adds the row Format Profile: Pages before the draft, with the count or "not known", and Page limit, with the limit of the row `(whole document)` or "no limit stated". `references/intake.md` lists both with their source.
3. The directions of the structure architect and of the draft writer give both values, and say that the length planned and written keeps the whole application within the page limit, and that the outline and the draft report state the room they assumed.
4. The message that ends the run gives the page count before the draft and after it, and says which of the two was over the limit.

### 3. What the criteria reviewer is given

1. The Quick start line of `review` is `/grant review <main.tex> [<file> ...]`: each further file is one the criteria ask about, such as a CV or a recommendation letter. A file that does not exist is the refusal "A missing input".
2. `review` compiles the application first (Steps 9, the compile alone), and the reviewer is given the compile's PDF. When the compile fails, or the runner has no `latexmk`, the reviewer is given the PDF beside the main `.tex` when one stands, and the message that ends the run and the review both say that the PDF is not of this run's compile, or that the reviewer read the `.tex` alone.
3. The reviewer is also given the file of form-field texts (item 7) when it stands, and each further file of the call.
4. `agents/criteria_reviewer_agent.md`, "What you are given", lists these, its rule on a criterion the files hold nothing on stays as it is, and the line "Files read" of `templates/criteria_review_template.md` names each file given.
5. `review` still changes no file of the application, and copies no PDF into its folder.

### 4. The citation style of a list set by hand

1. In `references/intake.md`, "draft", the default of the citation style, and in "revise" the value of the row Citation Format, is, in this order: the style of the `\bibliographystyle` line of an existing `main.tex`; the form the items of a `thebibliography` environment of that `main.tex` follow, named as "the form of the reference list set by hand"; else IEEE, a numbered style. A list set by hand is one opened by `\begin{thebibliography}`.
2. With a reference list set by hand and a `.bib`, the direction of the citation compliance agent says that the list's form is the style, that no item of the list is rewritten to another style, and that a key the `.tex` cites and the `.bib` lacks is listed with whether the list holds an item for it.
3. The message that ends the run says that the reference list is set by hand, so that a source the new text cites reaches the printed list only as an item added to it, and names each such source.

### 5. A font that stands in

1. The formatter's direction says that its report names each value of the "Layout" it could not set as stated, with what the `.tex` sets in its place, such as a font that stands in for the one the config names.
2. After each compile the session writes the log's lines on a font that TeX replaced into `checks.md` (`grep -n 'Font shape\|Missing character\|not loadable' <main>.log`), with "none" when there is none.
3. The message that ends a `draft` or `revise` run repeats each line of items 1 and 2, and `check` reports the lines of item 2.

### 6. A draft of one section is checked and reviewed on that section

1. In a `draft` run on one section, the direction of the citation compliance agent says that it judges the cited sentences of that section only, names the section by its heading, and keeps its results check to that section. Its lookups and its report are as its page gives them, and `lookup.py cite-keys` and `check-urls` still run on the whole `.tex`.
2. In such a run the session gives `/writing` a copy of the section:
   - it copies the application's folder to `review/` in the temporary folder, so that a file the section brings in stands beside the copy;
   - it finds the section's lines in the file that holds its `\section` or `\section*` line, the main `.tex` or a file it brings in, a commented line being no heading: from that line to the line before the next such line, or before `\end{document}`;
   - it writes those lines with `sed -n` to `section.tex` in `review/`, and invokes `/writing` on that file;
   - the stop "The writing findings" gives the file and the first and the last line number of the range, says that the review read the drafted section alone, and names `/writing <main.tex>` for a review of the whole application;
   - the draft writer's direction says that the findings' places are lines of `section.tex`, and gives it the file and the line the section starts on.
3. A `draft` run on the whole application, and every `revise` run, checks and reviews the whole application as now.
4. The incremental check after a later patch of a one-section run reads the cited sentences that patch adds or changes, as the `paper` skill's Steps 12 gives it.

### 7. The file of form-field texts

1. The skill defines one file of form-field texts, `grant-fields.md`, in the application's folder beside the main `.tex`. The skill names no other file for it and no marker.
2. Its format, stated in `templates/funder_config_template.md` or a template of its own, whichever reads better, and in the head comment of `check_limits.py`:
   - a line `## <Field>` opens a field, `<Field>` being the Field cell of the field's row in the funder config, matched letter for letter after the two characters `## ` with spaces at both ends taken off;
   - the field's text is every line after that heading up to the next line that starts with `## `, or the end of the file, with empty lines at both ends taken off;
   - a line before the first `## ` line belongs to no field;
   - a `### ` line, a fence and every other line inside a field are text of the field;
   - a heading matches a Field letter for letter, case included, since a form's field names can differ in case alone;
   - a `## ` heading that is no Field of the config gives no line.
3. The funder config's "Form fields" table keeps its four columns. Field is the field's name as the funder's form words it. The sentence that ties it to a marker key is taken out of the template, the config drafter's page and `SKILL.md`, and the config drafter reads the call documents and no other file of the application's folder.
4. `check_limits.py`:
   - keeps its three arguments, `check_limits.py <config> <pdf> <main.tex>`, and reads `grant-fields.md` in the folder of `<main.tex>`;
   - counts a field's text by the format above, in the unit of its row, a line break inside the text counted as one character whatever the file's line endings, and a byte-order mark at the file's start read as no character;
   - prints `not checked: <field>: <reason>` for a field when the file does not exist, with the file's path in the reason; when the file has no `## ` heading for the field; and when the heading has no text under it;
   - exits 2 with one `error:` line when the file exists and cannot be read as UTF-8, and when it holds the same `## ` heading twice;
   - takes `-` as `<pdf>` for a run that made no compile: the row `(whole document)` with a limit in pages then prints `not checked: (whole document): no compile was made`, and every limit in words or characters is counted as with a PDF;
   - holds no reading of any other file of field texts and of no marker.
5. A file of form-field texts that the user provides:
   - `config` asks at its intake, with the other questions, whether a file holds the texts of the form's fields, default none (`references/intake.md`, "config");
   - a file is in the format above when one or more of its lines start with `## ` and each such line names a Field of the config; such a file is copied with `cp` to `grant-fields.md` when it stands elsewhere, and checked with `cmp`;
   - a file in another format is read by a fresh agent started from a new page, `agents/field_texts_agent.md`: it copies each field's text, letter for letter, under the heading of the config's field it belongs to, into `grant-fields.md`, and writes a report to the run folder with, per field of the config, where in the user's file its text was found or that none was found, and each part of the user's file it copied to no field;
   - the session shows that report with the stop "The form fields", and the user confirms or corrects it, a correction going to the agent, resumed;
   - the user's file is never changed, which the session checks with `shasum` before and after;
   - a `grant-fields.md` that already stands is the stop "A file of form-field texts that exists", raised with the stop "A config that exists" before anything is written: the user says to replace it, to keep it, or ends the run;
   - the copy and the field texts agent run after the user has confirmed the config (`config` item 4), since they read its fields.
6. `draft` can write a field: `/grant draft <application folder> field <field> [<materials>]`, where the word `field` is followed by a Field of the config's "Form fields" table. The Quick start line of `draft` shows both forms.
   - A name after `field` that is no Field of the config is the refusal "A missing input", which lists the config's fields.
   - The run asks the intake of `draft` without the questions on the citation check, starts no structure architect, no argument builder, no citation compliance agent and no formatter, and makes no compile.
   - The draft writer is started with `config.md`, the materials, the main `.tex` when it exists, the field's name, its limit and unit, and `grant-fields.md` when it stands.
   - Its direction replaces, for this start, the two pieces of the `paper` skill's "Agent prompts" on the file the agent writes: the one file it writes is `grant-fields.md` in the application's folder, and it writes no patch. The direction says that a form field is plain text with no LaTeX command, since the form takes plain text and `check_limits.py` counts every character.
   - It writes the field's text under the field's heading, adding the heading when it is missing and the file when it does not stand, and changes no other line. The skill states this beside the exception of a new `main.tex`, since the patch scripts read `.tex` files.
   - The session copies a `grant-fields.md` that stands to the run folder before the start, and afterwards shows with `diff` which lines changed. A changed line outside the field is named in the message that ends the run with the copy's path, and the session restores nothing itself.
   - The session runs `check_limits.py` with `-` as `<pdf>`, and a field over its limit goes to the draft writer once more.
   - The closing `/writing` review, when the intake kept it, is invoked on `field.txt` in the run folder, a copy of the field's text made with `sed -n`, and the stop says that the review read that field alone.
7. Steps 9 on a runner without `latexmk` runs `check_limits.py` with `-` as `<pdf>`, so the limits in words and characters are still counted, and the user is told that the page limit was not checked.
8. The Stops table gains the rows "The form fields" and "A file of form-field texts that exists"; the sentence above the table that counts its rows, and each mode's line "Stops this mode can reach", are made true again; Rules says that the application's folder also gains `grant-fields.md`; and the run folder's list gains the field texts agent's report, the copy of `grant-fields.md` and `field.txt`.

## Decisions taken in this brief (each reversible, none silent)

1. The file of form-field texts is named `grant-fields.md` and stands beside the main `.tex`.
2. A field is opened by a `## <Field>` heading, and the Field cell is the field's name as the form words it.
3. `check_limits.py` takes `-` as `<pdf>` for a run with no compile, which a draft of a form field and a runner without `latexmk` both use.
4. A file in another format is copied by an agent with its own page, and the user confirms what went where at a stop.
5. A draft of a form field runs the intake and the draft writer only, and makes no compile.
6. The engine is read in the order of item 1, the application's own log before the packages it loads, and pdfLaTeX when nothing names another.
7. A draft that takes the application over its limit is reported with both page counts, and the run shortens nothing on its own.
8. A one-section draft gives `/writing` a copy of the section's lines in a copy of the application's folder, since `/writing` reads a whole file and the files it brings in.
9. `review` compiles the application to give the reviewer the rendered pages, and copies no PDF into the application's folder.
10. The skill's version stays 1.0.0.
11. A form field is drafted with the word `field` in the call, so that a field's name is never taken for a heading or for materials.
12. An empty field is `not checked:`, since a heading with no text is a field not yet written.
13. The glossary gets no entry for the file of form-field texts: the skill's own pages define it.
