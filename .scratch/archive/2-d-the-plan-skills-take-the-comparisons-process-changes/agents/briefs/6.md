## What to build

1. `docs/dev/blind-comparison.md`, one page, stating the protocol as ruled, each part once, in the order a comparison runs:
   - **The input.** One real input, the one the gate names, given unchanged to both sides: the new skill and the skill it is compared against. Each side runs in its own fresh session with only that input and its own skill; neither sees the other's output.
   - **Unlabelled.** Before judging, the person running the comparison removes from each output every mark of which side made it (a skill's name, a file or folder name, a header or footer a skill writes), writes the key (which output is which) to a file the judges are not given, and names the two outputs A and B.
   - **Random order.** Which output is A is decided by a command whose result the runner does not choose (for example `python3 -c 'import random; print(random.choice(["new first", "old first"]))'`), and the command and its output are kept with the key.
   - **The judge's input.** The judge receives the input and the two outputs and nothing else: no skill name, no gate, no statement of which output is expected to win.
   - **Reading.** The judge reads each output whole, and for each lists its critical failures before stating any preference. A critical failure is one that makes the output unfit for the purpose the input sets (a claim the input contradicts, a missing part the input asks for, a citation that does not resolve), each quoted with its place.
   - **The verdict.** A, B or a tie, written with the reasons, each reason pointing at the failures or the passages it rests on.
   - **Twice, the order swapped.** The comparison is judged twice, the second time with A and B swapped. Each judgment is made by a fresh agent, so the second judge has no memory of the first. When the two verdicts name different sides, the result of the two judgments is a tie.
   - **The final call.** The user reads the input, both outputs and both verdicts, and makes the final call: the new skill wins, ties or loses. The user's call is the result the gate reads; "wins or ties" in a gate means the call is a win or a tie.
   - **The record.** The comparison is kept in the ledger of the plan whose gate needs it, at `agents/reviews/<step>-blind-comparison.md`: the input or its path, the two outputs as judged, the key and the command that set the order, both verdicts as the judges wrote them, and the user's call with the reasons.
2. The page opens with one paragraph saying what it is for (a gate that compares a new skill with another skill cites it) and who runs it (the orchestrator of the plan whose gate needs the comparison).
3. `docs/dev/change-standard.md` line 21: the sentence "A gate for a judgment is a review: the user's, or a blind comparison." gains a pointer to the page, so the term used there resolves: "A gate for a judgment is a review: the user's, or a blind comparison, run as `docs/dev/blind-comparison.md` says." ## Decisions taken in this brief (each reversible, none silent)

1. "A fresh agent judges twice" is read as a fresh agent for each of the two judgments, so the second judge cannot carry the first order into the second; one agent judging both orders in turn would remember which output it preferred.
2. Both sides run in fresh sessions with only the input, so neither output is shaped by the other or by the session's earlier context.
3. The order is set by a command whose output is kept, so the record shows the runner did not choose it; this is a one-line command, not a script file.
4. The record lives in the ledger of the plan whose gate needs it, so it is archived with that plan.
5. The page names the person who makes the final call "the user", as the repository's pages do; the ruling's "Axel" is that user.
6. The rules file's one sentence that names a blind comparison points at the page (item 3), so the term the rules file uses resolves to the one place that defines it; the sentence's rule is unchanged.
