## What to build

1. The sixteen folders move, each whole, with `mv`: `roadmap`, `grill`, `plan`, `spec`, `refute`, `land`, `plan-orchestration` and `plan-retro` into `skills/orchestration/`; `repo-setup`, `ordo-init`, `ordo-help` and `session-retro` into `skills/ordo/`; `code-comments` and `diagnose` into `skills/code/`; `paper` and `writing` into `skills/academic/`. No file inside a skill folder is renamed. `skills/` then holds the four group folders and nothing else.
2. A skill stays installed under its own name, in one flat folder, such as `~/.claude/skills/plan`. The text of a skill that reaches another skill does so as an installed skill does, by the other skill's folder beside its own, and is not rewritten to a group path. A script or a test that reaches another skill's file by a relative path works in both places: installed, where the skills are side by side, and in the repository, where they are grouped. `check_config.py` finds the `plan` skill's `templates/plan.yaml` beside its own skill folder and, when it is not there, in a sibling group folder; `check_config.test.sh` finds the two example files the same way; every other such path that `grep -rnE '\.\./|"\.\."|pardir' skills utils` prints is read, and fixed when the move breaks it. When the `plan` skill is in neither place, `check_config.py` prints an `error:` line that names the two places it looked in and exits 1, and its head comment lists that error.
   - `/ordo-help skills` prints the sixteen skills in both installations: copied flat, and linked by a pin of a grouped tag, where the real parent of the skill's folder is a group folder. `skills/ordo-help/SKILL.md` says how the skills folder is found in each, and its description and `README.md:23` stay true.
3. `utils/pin.sh` reads three layouts of a tag and of the pinned worktree: grouped (`skills/<group>/<name>/SKILL.md`), flat (`skills/<name>/SKILL.md`) and top level (`<name>/SKILL.md`).
   - A skill is named by the folder that holds its `SKILL.md`. Its link is `<skill folder>/<name>`, pointing at that folder in the pinned worktree, whatever its group.
   - A tag may hold skills in the grouped and the flat layout at once. The top level is read only when `skills/` holds no skill. A `SKILL.md` anywhere else in the tag, such as one inside a ledger folder, is no skill.
   - A tag that holds two skills of one name is refused before anything changes, with a `pin: ` line that names both paths, two groups or the flat and the grouped place alike.
   - Every place that builds a skill's path from `skill_root` today (the linking, `check_links`, the refusals, the removal of a link whose skill the tag lacks) uses the skill's folder as found.
   - A link into the pinned worktree at a skill's place in an earlier layout is replaced on a pin by the link to its place in the tag, and check mode reports such a link with one line that says it does not link to the skill's folder in the pinned tag, never that the tag lacks the skill. A pin of an older tag over a grouped pin puts each link back at the skill's place in that tag.
   - The summary lines, the exit statuses and every refusal the head comment states stay as they are. The head comment states the three layouts and the refusal of a doubled name, and says nothing that is no longer true.
4. `utils/pin.test.sh` keeps every case it has, on the flat layout it builds today, with the fixture's folder written through a variable so that the gate's line prints no line of the test, and adds these:
   - a tag in the grouped layout, with two groups and a skill in each, pinned: each skill is linked under its own name to its folder inside its group, the skills line counts them, and check mode passes;
   - a pin of a flat tag followed by a pin of a grouped tag of the same skills: each link then points into the group folder, and no link to the earlier place is left;
   - a tag with one skill name in two groups: refused with exit 1, the skill folders and the pinned worktree as before; the same for one name in the flat and the grouped place;
   - a pin of a grouped tag followed by a pin of a flat tag of the same skills: each link points at the flat place, and check mode passes;
   - on a grouped pin, a link moved by hand to the earlier place: check mode exits 1 with the one line of item 3;
   - a grouped tag that lacks a skill an earlier grouped tag held: the link is removed with its line, and the links of the skills held stay;
   - a tag that tracks a `SKILL.md` inside a ledger folder under `.scratch/`: it pins, and that file gives no skill and no doubled name.
   Each new case prints a line with its name when it passes, so the report can quote that each ran.
   The test's head comment names the new cases with what their failure costs.
5. The README: the copy loop copies each of the sixteen skills from its group folder into the flat skill folder, and a skill it does not find stops the loop with a message, so that a copy that installs fewer than sixteen skills cannot pass unseen. The table of skills, the text on the CLI route, the `<skills>` placeholder of lines 163 to 202 and every sentence that names a skill's path say what holds in the grouped layout and in an installation.
6. Every path in the tracked files outside `.scratch` that names a skill folder names its new place: the 215 lines above, the ADRs and the roadmap included, `.agents/plan.yaml`'s `standards` value, the commands of `docs/dev/building.md`, and `docs/dev/skill-layout.md`'s `skills/<name>/SKILL.md` and its glob and `docs/dev/change-standard.md`'s `skills/*/SKILL.md`, which take the grouped form. A path is rewritten and the sentence around it left alone, unless the sentence is false in the grouped layout, in which case it is corrected. `docs/dev/scripts.md` and `docs/dev/building.md` are kept in step with the scripts as the change standard asks.
7. No `metadata.version` is raised in this step: `docs/dev/skill-layout.md`, "Frontmatter", has a plan raise one part of a skill's version once, and the skills whose text this step changes (`grill`, `ordo-help`, `ordo-init`) are raised by steps 1 and 3 of the plan.
