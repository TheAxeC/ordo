### 2. `skills/code/wizard/SKILL.md`

2.1. Frontmatter as the layout gives it, with `name: wizard`, `metadata.version: "1.0.0"` and no `disable-model-invocation` key. The description carries the source's three parts: what it generates, when to use it (provisioning infrastructure, setting up credentials or CI secrets, walking an unfamiliar third-party dashboard, a one-off migration or cutover), and that it is not for steps the agent can perform itself.

2.2. The nine sections of the skill layout. Steps carries the source's four process steps in order, each with its "Done when" criterion and every requirement the source states under it:

- Scope the procedure: read the repository first (the files the source lists for a setup, and the current state, target state and irreversible actions for a migration), show the user the ordered list of stages and the values each produces, and wait for the user's confirmation, with stages added, dropped or reordered as the user says. For each captured value: where the person gets it, where it is written (`.env`, a GitHub secret, a GitHub variable, several of these, or nowhere for a pure action; the GitHub variable is ruling D2 of `plan.md`, and the template's `set_var` writes it), and whether it is secret.
- Map each stage's journey: the URL, what to do there, where the value is shown, which variable it fills. Where the current UI or command is not known, say so and ask the user or read the service's documentation; never invent a step.
- Author the script: copy `templates/template.sh` of this skill to the target path, replace the example stage with one `stage` per step in dependency order, use the library's helpers, set `TOTAL_STAGES`, keep the template's rules (the URL opened before its value is asked, `ask_secret` for every secret, `write_env` for every persisted value, `set_secret` only for the values CI needs, `confirm` before every irreversible action, one focused task per stage), and never edit the library above the marker.
- Verify and hand off: `bash -n <script>`, `shellcheck` when it is installed, `chmod +x`, never run the script (it opens a browser and waits for a person), trace it by reading (every value of the scope is captured and lands where the scope said, every `set_secret` name equals a `secrets.*` reference in CI), and tell the user how to run it, and to delete it after its run unless it is kept as 2.3 says.

2.3. The source's rule on where the script lives is kept and made a rule of the skill, in these terms: the script is written to a scratch path or a `scripts/` path the user names, it is deleted after its run unless the user wants a repeatable setup path, and it is committed and linked from the README only on the user's word.

2.4. Stops has the row for the stage list the user confirms, and a row for a step whose UI or command is not known. Rules holds: the session never runs the script and the library above the marker is never edited, both from the source; and a secret is never asked for in the conversation, never printed and never written into the script, which the plan's goal asks for ("never printing a secret").

2.5. Where the skill names the template's example stage, it says the example is made up, around the public API-keys page of Stripe's dashboard.
