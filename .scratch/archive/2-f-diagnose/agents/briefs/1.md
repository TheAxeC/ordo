## What to build

1. `skills/diagnose/SKILL.md`, a new skill, `metadata.version: "1.0.0"`, following `docs/dev/skill-layout.md` in every section and rule (frontmatter with a description of at most 1024 characters and its triggers, the nine sections in order, one action per Steps item, each item ending on its completion criterion, one rule per bullet). Each rule below is written once, in the place "Where a rule goes" gives it (a point of the work in its Steps item, a tempting shortcut in Anti-patterns with its reason, a rule that holds throughout in Rules), and any other place that needs it names that section. The skill names the rules file's rules by what they say ("the rules file's rule that a defect in code begins with a test that fails", "the rules file's rule on secrets in quoted command output"), never by number or path, and says "a defect in code" as the `repo-setup` template of the change standard does. Its content is the requirements below; the wording is the builder's, in the prose standard.
   - **Invocations**: `/diagnose <symptom>`, the symptom in the user's words; `/diagnose <entry> <step> <finding>`, inside a plan, where `<finding>` is written as the refuter report names it (its heading and number, such as `Spec 1`), or as `red line` for a red line at the step's landing whose cause is not known, or as `brief check <n>` for a brief-check finding.
   - **Who is present**: the wait for the user (below) depends on who runs the skill, never on the invocation: a person running it, by hand or inside a plan they run step by step, gets the waits; a session running under `plan-orchestration` gets none, and its hypotheses reach the user as the hypotheses item says.
   - **Use instead**: at least `/refute <entry> <step>` for reviewing a built step; `/spec <entry> <step>` when the cause is known and a step is to be prepared; `/ordo-help <entry>` for where a plan stands.
   - **What it reads**: the symptom, quoted exactly (the user's words, or the finding's failure scenario from the report that holds it); the rules file and standards `.agents/plan.yaml` names, and `docs/glossary.md` and the ADRs in force as the `spec` skill's "What it reads" 5 says, when the repository has them; inside a plan, the ledger folder, the step's dispatch entry (worktree, base), its brief, and the report the finding is in (the refuter report `agents/reviews/<step>-refuter.md`, the brief check's report, or the landing's red line in the state file). Inside a plan, a missing ledger folder, dispatch entry, report or finding is a refusal naming it. With no rules file, the skill's own Rules state the rules it needs in full: a defect in code begins with a test that fails; a guard is not a fix; a secret in quoted output is written `<REDACTED>`.
   - **Where probes run**: run by a person outside a plan, in the user's checkout or worktree. Inside a plan, on a scratch copy under `$TMPDIR` that shares no files with the step's worktree: `git worktree add --detach <tmp> <base>` from the main checkout, then the step's diff, `git diff <base>` run from inside the step's worktree, applied in it with `git apply`, and the untracked files `git status --porcelain --untracked-files=all` lists there copied in (every git command on a worktree runs from inside it, never as `git -C`, as the `spec` skill's Rules say); removed at cleanup with `git worktree remove --force <tmp>`. The step's worktree is never changed, so the rule "diagnosed by the orchestrator, read-only" holds. A red command that would touch the user's real home, installed skills or pinned checkout runs with those paths redirected under `$TMPDIR` (such as `HOME`, `ORDO_STABLE` and `ORDO_SKILL_DIRS`, as `utils/pin.test.sh` sets them), or not at all without the user's leave.
   - **The red command** (the first Steps item of the work; a hypothesis formed, or code read to form one, before it has been run red is an Anti-patterns row, which the item names): one command, run and its output quoted, that drives the code path of the symptom and goes red on the exact symptom (the error text, the wrong output), never on "it did not crash"; the same verdict on three runs in a row, or, for a symptom seen only sometimes, a failure rate measured over a stated number of runs and raised (more runs, parallel runs, narrowed timing) until it is high enough to probe against; tightened once it exists (faster setup, a sharper assertion on the symptom, time pinned, random seeds fixed, the file system isolated under `$TMPDIR`, the network cut) and run unattended in seconds where the symptom allows. For a slow case, a baseline first: the known-good version or the requirement measured over repeated runs with the mean and the spread, and red defined as a threshold stated from it. The ways to build one, in order of preference: a failing test at the level that reaches the defect; a command-line run on a fixture with its output compared to the expected output; an HTTP request against a running server; a headless-browser script that drives the view and asserts on what it shows; scratch files or a scratch repository under `$TMPDIR` that reproduce the state; a replay of a captured input; a small harness calling the code path directly; a loop over many generated inputs for "sometimes wrong"; `git bisect run` on a scratch clone when the defect appeared between two known states; the same input through two versions with the outputs compared; and last, for a symptom only a person can trigger, a script that prints each action for the user to take and reads back what they observed, which is a stop that waits on the user.
   - **A defect in text** (a skill, a page, a rule, a brief whose instructions led to the wrong behaviour): the red is the quoted text beside the line of a run or transcript that shows the wrong behaviour it led to; the other items apply, and the fix is by reading (below).
   - **When no red command can be built** (every way tried; or the scratch copy cannot reproduce because the symptom needs the real environment, or a credential the environment lacks): run by a person, a stop that lists every way tried with what it gave and asks for access to where the symptom occurs, a captured artifact (redacted, quoting only the lines that carry the symptom), leave to add temporary instrumentation, or the credential set in the environment; under `plan-orchestration`, the cause not found (below).
   - **The case shrunk**: once red, each part of the case (input, caller, configuration, data, step) is cut one at a time with the red command rerun after each cut, a cut that turns it green put back; the cuts and their results are recorded; the item is done when removing any remaining part turns it green.
   - **The hypotheses**: three to five, ranked, formed only after the case is shrunk, each written as "If <cause>, then <change> turns the red command green" (and, where it helps, "<another change> makes it worse") and naming the result that would falsify it. A hypothesis whose falsifying result cannot be named is sharpened or dropped. They are shown to the user with the red command and the shrunk case: a person gets them and the skill waits for the reply before the first probe (a stop); under `plan-orchestration` they are written into the diagnosis record, quoted in the round brief and in the landing report beside the record's path, and the skill goes on (ruling "Step list" D2).
   - **Probes**: each tests one hypothesis, named by its rank, and changes one thing; the red command is run after it and the result recorded with the verdict (falsified, or still standing); the change is undone before the next probe unless it is the fix. A debugger or an interactive session is used where the language has one; otherwise logging at the boundaries that separate the hypotheses; any logging a probe adds carries one tag unique to the diagnosis (such as `DIAG-<4 hex digits>`). When every hypothesis is falsified, a second list is formed from what the probes showed and shown as above.
   - **The cause not found**: when the second list is falsified too, or no probe can separate the hypotheses left, or no red command can be built under `plan-orchestration`, the cause is not found: the record says so with every probe; inside a plan it is raised to the user as an open item, as `plan-orchestration`'s "Only known fixes" says; run by a person, it is shown and the skill stops.
   - **The cause**: the hypothesis the probes left standing, stated with the probe that shows it: the red command green with the change and red without it.
   - **The fix and its test**: a defect in code whose failure costs something (by the rules file's rule that a test exists only for behaviour whose failure costs something) gets a test that reproduces the shrunk case at the place the defect occurs; the test is run on the tree before the fix and its failure quoted, then the fix is made, the test run green, the red command run green, and the original unshrunk case rerun green. A place where no test can reach the defect as it occurs is written in the diagnosis record under "No test reaches it", with the reason. A defect in text is fixed by reading, with the text quoted before and after and no test. Inside a plan, all of this is done on the scratch copy, both runs of the test quoted, and then the fix and the test go to the builder as the repair round's ruling, as `plan-orchestration`'s Steps 8 sends a round; the skill does not change the step's worktree.
   - **Cleanup**: the tag's grep prints nothing; the scratch copy and every throwaway file are removed, a credential or `.env` file copied into `$TMPDIR` among them; the red command is rerun on the original case and is green (run by a person outside a plan) or the round carries it as the check (inside a plan).
   - **Where the cause is written**: outside a plan, the last bullet of the commit message states the cause, the red command and the fix's test; inside a plan, the diagnosis record (item 2) is saved in the ledger at `agents/reviews/<step>-diagnosis.md`, a later diagnosis of the same step appended below the earlier one under its own heading naming its finding; the round brief quotes the cause and the landing's booking names it.
   - **Redaction**: every quoted command output carries `<REDACTED>` in place of a secret, as the rules file's rule on secrets in quoted command output says; a captured artifact is quoted only in the lines that carry the symptom; a red command takes a credential from the environment, never from a file into its command line or the record; when the redacted output is not enough to diagnose, the skill says so and asks the user (a stop, run by a person; under `plan-orchestration`, the cause not found).
   - **Stops**: the hypotheses, run by a person; no red command can be built, run by a person; a red command a person drives; not enough output after redaction, run by a person; the cause not found. Refusals where an input inside a plan is missing.
   - **Anti-patterns** at least, each stated there once with its reason, the Steps item it guards naming the Anti-patterns section instead of restating it (a guard for a fix cites the rules file's rule that a guard is not a fix): a hypothesis before the red command; a red command that asserts only that something ran; two changes in one probe; a probe tied to no hypothesis; a test written after the fix; a guard for a fix; untagged logging; logging everything and searching afterwards.
   - **Rules** at least: the rules stated in full for a repository with no rules file (above); the skill never runs against the user's real home, installed skills or pinned checkout without leave.
2. `skills/diagnose/templates/diagnosis.md`: the diagnosis record the skill fills in, used by both invocations (by hand it is shown to the user, inside a plan it is saved in the ledger): the symptom quoted; the red command with its runs quoted; the cuts of the shrunk case and their results; the ranked hypotheses with their falsifying results; each probe (hypothesis rank, the one change, the run, the verdict); the cause with the probe that shows it, or "cause not found" with every probe; the fix and its test with the failing and passing runs quoted, or the text before and after; "No test reaches it" with the reason when that is so; the cleanup's grep. Placeholders in the form the other templates use (read `skills/spec/templates/brief.md` and `skills/refute/templates/report.md` for it).
3. The terms: `skills/repo-setup/templates/plan-terms.md` gains each term the skill uses in a sense the glossary does not define, in alphabetical place, each with "Stated in:" naming the `diagnose` section: at least **red command**, **hypothesis** (one of the ranked causes, with its falsifying result), **shrunk case**, **case, of a diagnosis** (the scenario that reproduces the symptom; the original case is that scenario before it is shrunk), **diagnosis record** and **cause not found**. **Probe** already has a sense in use (the **premise** entry and `spec`'s "a grep or a probe": a command run to check a claim about the tree); one entry gives both senses, the diagnose sense being one change tied to one hypothesis with the red command run after it, and names both "Stated in" places.
