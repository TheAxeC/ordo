## What to build

When the part is done, a diagnosis that has found its cause fixes the same defect at every place it occurs, not only at the operation that showed the symptom, and never tells the user that a part of the symptom did not happen without reading the code that would make it happen.

### The same defect at other places (`skills/diagnose/SKILL.md` Steps 15, 18 and 19)

1. The cause's rule is stated at the kind of value the operation reads: how a value of that kind must be read or treated (for a path, "a path is read as the folder it names, whatever its spelling"), and never only as what the one operation does with it ("two names of one folder must compare equal"). The record's Cause section and its "Operation and other inputs" section state it so.
2. With the cause stated, the session finds every place of the defect: every operation of any kind (a comparison, a derivation, a lookup, a write, a parse) that reads a value of that kind against that rule and breaks it. It searches the code the red command drives and the code that feeds it, reading forward from every place values of that kind are read or assembled (every source, such as each environment variable, configuration entry or default that supplies one) to every operation that uses them, as it already reads back from the shrunk case for the other inputs. The operation the cause names is the first place; each other one is a further place of the same defect, named in the record with its file and line, or its section for a defect in text, and the rule it breaks.
3. The three classes keep their names and are defined by places:
   - part of the defect: wrong on the tree without the fix at a place of the defect;
   - not part of the defect: right on the tree without the fix;
   - another defect: wrong on the tree without the fix only at an operation that breaks another rule.
   An input wrong at a place of the defect and also at an operation of another rule is part of the defect, and its wrongness at the other operation is named in the record as another defect. Every place the class definitions are stated or restated (Steps 15 to 19, the template, the glossary) says this, and Steps 15 line 196 is reworded so it holds for every place of the defect.
4. Each other input is run against every place of the defect it reaches, with its right result, so an input wrong only at a further place is found, classed part of the defect and given a test case by Steps 16. The glossary entry **right result, of an other input** is reworded so the result is the one the cause's rule gives, at whichever place the input is read.
5. The fix (Steps 18) covers every place of the defect, the operation the cause names and each further place. Where the places can share one change (a helper every place calls, or one written form made at every source the values come from), the fix is that change; otherwise it is one change at each place. Every source a value of that kind comes from is covered. Steps 18 lines 230 to 233 are reworded to say this: the fix is made at the places of the defect, starting from the change of the probe that shows the cause, never one change per spelling. A fix that leaves a place of the defect unchanged is not done, and the Done line says so.
6. Steps 18 and 19 hold every input not part of the defect at its right result after the fix, as it was without it. An input of another defect is left out of the result and the fix is not widened to make it right; line 233's "gives what it gave" no longer applies to an input of another defect, since a change at a source can change its result.
7. Steps 19 runs every input part of the defect, at whichever place it was wrong, and each gives its right result.
8. A further place found only after the fix is made goes back through items 2 to 7, inside the count of two changes Steps 18 already sets: the second change may widen the fix to the new place.
9. For a defect in text, the kind of value is the kind of situation the instruction governs, and a further place is another instruction of the same text that governs a situation of that kind against the same rule.

### A part of the symptom the red command does not catch (`skills/diagnose/SKILL.md` Steps 4 and the final message)

10. In Steps 4, each part of the reported symptom is listed in the record with whether the red command catches it: its assertion is red on the red runs. A part with no assertion, or whose assertion passes on the red runs, is a part the red command does not catch.
11. Once the red command has been run red on its other parts, each part it does not catch is read in the code that would produce it, along the path the red command drives. This reading forms no hypothesis: it asks only whether the code produces the part on that path. The text says so beside Steps 4 line 105 and the Anti-patterns row on code read before the red, so the two do not read as a clash.
12. When the code produces that part on the red command's path, the red command is changed to catch it where it happens (an output line, an intermediate state, an assertion before the run ends), since an assertion on the end state can pass when the run undoes its own change. The part is then red and asserted like the others.
13. Only a part that the code, read along that path, does not produce is written as not reproduced, with the lines read and why they do not produce it.
14. No statement about what the code does (a rule such as "this only removes the links the new version dropped") goes into the record or the session's final message without the lines it rests on, read in this run. It is a rule for the whole skill, so it goes in "Rules", as `docs/dev/skill-layout.md`, "Where a rule goes", puts a rule that holds throughout a skill.
