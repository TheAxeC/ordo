## What to build

Nine defects, each with what must hold when it is fixed. Items 1 to 6 are in `skills/ordo/ordo-init/`, items 7 to 9 in `skills/code/codebase-design/SKILL.md`.

1. **A new repository is set up without a run of any verification command.** When "Steps / A new repository" follows the existing-repository steps on the tree it just wrote, no command meant for the verification page is run, whether the user named it in question 3 or the skill read it from a build file it wrote, since the tree holds no source for it. Each is written on the verification page as named. The draft of the configuration says, beside each, that it was not run and why. The stop "A failing command" is not reached from the new-repository case. In an existing repository the one run stays as it is. Every sentence that states the one run or its result is given the new-repository exception: "Steps / An existing repository" 3 and 12, the Rules sentence on the two exceptions to writing nothing before approval, and the Stops row. Rules gains one sentence: a command that fails is shown as failing and left as it is, and no step writes a test, a source file or any other file so that a command passes.
2. **The shared rules name no fixed path for the prose standard.** In `templates/shared-rules.md` the Prose rule's second sentence reads: "The standard is the repository's prose standard, and it applies to every comment, page and message." Nothing else of the block changes. `templates/CLAUDE.md` is changed only if a sentence of it becomes false.
3. **A glossary written in a configured repository is listed.** When "Steps / A configured repository" 10 drafts a new glossary file and the plan configuration found lists no glossary in `standards`, the drafted change includes the glossary's path added to `standards`, relative to the folder that holds the configuration file, shown as a diff with the rest of the change and written with it. A configuration with no `standards` key gets the key with that one path and the comment "Steps / An existing repository" 9 gives a written key. In the `projects:` form the list is that of the project the call names, and with none named, of the first project. Each open plan's configuration block gets the same path on its `standards` line, as `grill`'s "Steps / Writing what settled" does for a glossary it creates; read that step and state the same. After the write, the later sync runs take `--glossary`, as item 7 of those steps says of a listed glossary.
4. **A file git ignores is written, left ignored, and kept out of the commit.** Before the skill drafts a file to create or a change to a file that exists (`CLAUDE.md`, the glossary, a page), in each of the three cases, `git check-ignore -q -- <path>` is run for it on the folder as it stands. A path git ignores is still offered, and written or changed on approval. The draft says, beside that file, that git ignores it and names the line and the ignore file `git check-ignore -v -- <path>` prints, which may be a file outside the repository. The skill never changes that ignore rule, never offers to, and never forces the file into a commit. The path is left out of every `git add` and `git commit` command the skill writes, since `git add` exits 1 on an ignored path even when it stages the others. When every file written is ignored, no commit is made and the last message says so. Each stop or last message that lists the files written lists such a file apart, as written and ignored by git, so the reader does not look for it in `git status --short`. The three ignore checks that exist (the worktree root, the configuration file, and the check of "Steps / A new repository" 10) stay as they are.
5. **A default coding-standards page written into a repository names no tool the repository does not configure.** This holds for the common page and the three language pages, in every case that writes one. A tool (a formatter, a linter, a static type checker run as its own command) counts as configured only when the repository holds its configuration file or section, or the user named it in an answer. A language's own compiler and its configuration file are not such a tool. For a tool that is not configured, each rule of the page is split by requirement, as `codebase-design`'s "Steps / standards" 5 splits a rule that names a tool: a requirement that can be read and followed without the tool is written in plain words without the tool's name, its rule codes or its configuration file; what only the tool can do (that it runs, its configuration, a selection of its rule groups) is left out. A line that names a rule code of the tool names the tool. The draft lists, in one line per page, the tools left out. This rule is stated once in `SKILL.md`, where the pages' placeholders are filled, apart from the rule on "checked by reading at review", which is for a placeholder; the template pages stay as they are.
6. **A skill finds another skill's folder where it is installed.** `ordo-init`'s "What it reads" 2 and 3 and its Rules sentence on "the templates of the `plan` and `roadmap` skills beside it" state the order `templates/check_config.py` uses to find the `plan` skill's folder (its function `plan_skill()` and head comment): from this skill's folder with every link resolved, the folder of that name beside it, and otherwise the folder of that name in a group folder beside this skill's group folder. The `roadmap` skill's folder is found the same way. A folder found in neither place is named, with both paths, in the message the skill then gives. The same sentence is wrong in every skill that says the `ordo-init` folder "stands beside" its own: `skills/code/codebase-design/SKILL.md` (two places), `skills/academic/writing/SKILL.md`, `skills/code/code-comments/SKILL.md`, `skills/academic/paper/SKILL.md` (two places), `skills/academic/grant/SKILL.md` (two places), `skills/academic/referee/SKILL.md` (two places), and ADR 0047 (two places). Each gets the same order in the same words, with `ordo-init` as the folder looked for. Find every place with `git grep -n 'beside this skill\|beside it\|standing beside' -- skills docs/adr README.md`, and say in the report what each hit was and what it now reads.
7. **An estimated count is shown as an estimate.** In "Steps / standards", a count a command produces by listing each place is written "<n> of <m>" as now. A count produced by a pattern over lines, which can miss or over-count, is written "about <n> of <m>" in the draft and in the audit file, and the audit file's line for that rule says the count is an estimate. An estimate within one tenth of <m> of half of <m>, on either side, puts the rule in group 4, which adds nothing unless the user names it; any other estimate sorts by "more than half" as an exact count does. The made-up example of the draft shows one estimated count.
8. **A default rule that the repository's pages contradict is a difference.** Group 1 also takes a default rule where a page of the repository, one compared or one noted at item 3 of those steps, states or describes the opposite: a rule that asks the opposite, or a described practice the default rule forbids. The noted pages are read for this and for nothing else, and the sentences that say only the compared pages are read (item 3, and the draft's sentence on pages "not compared") are reworded to say so. Such a difference is shown in full like every difference, with the repository's sentence quoted and its page and section named; the sentences on the form and the words of group 1 are reworded so that they fit a described practice as well as a rule. Such a rule never stands in group 2, 3 or 4.
9. **Present, and a difference, each by one criterion.** The sorting text of item 5 is rewritten so that these hold, each stated once:
   - Present, the repository asks at least as much: the repository's rule covers what the default rule covers and asks the same or more of it. A default sentence that takes a kind of file or a kind of defect out of a requirement, or that allows what the repository's rule forbids, is an exemption however it is worded, and makes no difference.
   - Present, the default says more where the repository is silent: the sentence that exists on a default rule that "holds more than the repository's rule" stays, and is set apart from the next bullet.
   - A difference: the default rule forbids or requires something that the repository's rule expressly allows or expressly sets otherwise (a different limit, a different order, a different check, an allowance the default withdraws). The clause "whether or not the two can both be followed" is replaced by this criterion.
   - The made-up example's difference A (the whole verify list before reporting against the checks of the changed files) is a pair that is now present. It is replaced by a made-up pair that is a difference under the criterion, and the example's count of rules already present is kept consistent with it.
   - The text gives one made-up example of an exemption and one of a default that allows what the repository forbids.

For every item: the change is made everywhere the skill states the behaviour (the steps of each case that reach it, the Stops table, Rules, Anti-patterns, the reference page), so that no two sentences of a skill disagree. Item numbers of "Steps" and "What it reads" are kept: a new requirement is a sub-bullet of the item it belongs to, since `docs/glossary.md` and `plan-terms.md` cite items by number; where a number must change, every citation of it is corrected. No `metadata.version` rises: `docs/dev/skill-layout.md` raises a skill once per plan, this plan has raised `ordo-init` to 4.0.0, no release holds `codebase-design` yet, and the five other skills change in one sentence that changes no behaviour. A frontmatter description is changed only where the step makes it false; the two descriptions have 11 and 5 characters left under 1024. `README.md`, `docs/glossary.md` and `skills/ordo/ordo-init/templates/plan-terms.md` are corrected only where the step makes a sentence of theirs false.
