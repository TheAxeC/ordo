## What to build

1. **`skills/land/templates/checks.sh <state file>`** (new), run from the root of the checkout it checks. It needs `python3` with PyYAML and `bash`.
   - It reads the `verify:` key of the state file's first fenced block whose info word is `yaml` or `yml`.
   - It runs each command in order through `bash -o pipefail -c '<command>'`, from the directory it was started in, with standard input from `/dev/null` and standard output and error together.
   - Before each command it prints `$ <command>` on a line of its own, then the command's output.
   - At the first command that exits non-zero it prints `checks: failed with exit <status>: <command>` and exits 1; the commands after it do not run.
   - When every command exits 0 it prints `checks: <n> commands passed` and exits 0.
   - It refuses with a message starting `checks: ` and exit 2, before running anything: no argument or more than one; a state file that is missing, unreadable or not UTF-8; no `yaml` block, or one not closed or not valid YAML; no `verify:` key, a `verify:` that is not a list, an empty list, or an item that is not a non-empty string. A list it cannot read never passes.
   - Its head comment states what it computes, its input, its output and its exit statuses, in that order, and nothing else.
2. **`skills/land/templates/checks.test.sh`** (new): three cases on scratch state files under `$TMPDIR`, each asserting the exit status and the line named: a list whose second of three commands fails exits 1, prints `checks: failed with exit <n>: <that command>` and does not run the third (the third writes a marker file that must not exist); a list of passing commands exits 0 and prints `checks: 2 commands passed`; a state file with no `yaml` block exits 2. It ends with `PASS: checks.sh scratch tests` and exit 0, or a `FAIL:` line and exit 1.
3. **`skills/land/templates/land.sh`**, rewritten as the only landing script, run from the repository root as `sh <the land skill's folder>/templates/land.sh <state file> <step> <base>`:
   - `<state file>` is the plan's `orchestrator-state.md`, relative to the repository root or absolute; `<step>` is the step's branch, which is also its worktree folder's name; `<base>` the recorded base.
   - It reads `.agents/plan.yaml` with `python3` and PyYAML. One-project form: `worktree_root` (default `.agents/worktrees`) and `ledger_root`. `projects:` form: the project whose `ledger_root` holds the state file, and that project's `worktree_root`; the worktree's add excludes that `ledger_root`. No `.agents/plan.yaml`, no `ledger_root`, or a state file under no project's `ledger_root` is refused with exit 64 before anything is touched.
   - It keeps the git work of today's script unchanged in behaviour: the preflight, the resume of a landing stopped after its checkout, the bounded `index.lock` wait with its stale-lock rule and `LANDING_LOCK_WAIT`, the add with the ledger root excluded (the whole tree, no tool directory), the wip commit, the checkout of `<step>-land` with the ledger root as an ignore pattern, the empty range printing `nothing to copy: <base>..<step> holds no commit`, the cherry-picks, the conflict printing its paths and exiting 2.
   - After the cherry-pick on main it runs `sh <its own folder>/checks.sh <state file>` from the repository root; a non-zero exit fails the landing with exit 1 and `checks.sh`'s output printed. Its own folder is `$(dirname "$0")`; it looks nowhere else.
   - It then prints the booking data: the diff stat against `<base>` and the staged paths. No usage rows, no `node`: the lock's age is read with `python3` (`os.stat(...).st_mtime`).
   - No `ADAPT` line or block, no `find_template`, no `--no-browser`, no `--session`/`--since`. The head comment states what it does, its arguments, what it reads, its exit statuses (0 landed and checked, 1 a failed check or a stop, 2 a conflict, 64 a refusal of its arguments or configuration), in that order, and no history.
4. **`skills/land/templates/land.test.sh`**, rewritten to four cases on scratch repositories under `$TMPDIR`, each with a `.agents/plan.yaml`, a ledger under `ledger_root` holding an `orchestrator-state.md` whose `verify:` list the case sets, and a step worktree under `worktree_root`; `land.sh` and `checks.sh` are run from this file's own folder:
