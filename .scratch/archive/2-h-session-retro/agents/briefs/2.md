## What to build

1. `skills/session-retro/SKILL.md`, in the layout of `docs/dev/skill-layout.md`, `metadata.version` "1.0.0", the description at most 1,024 characters by the standard's command, its `Triggers on:` with a phrase for each invocation and no phrase that `plan-retro`'s lists or that asks for `plan-retro`'s case (such as "retro" or "run a retro"). Words: a transcript's session is "a Claude Code session", never "the session", which keeps its glossary sense; a point is "a keep point" or "a change point", never a "kind"; the user's answer to a proposal is "the decision", never a "ruling"; the noun "retro" is used only for `/plan-retro`'s report, the names `session-retro` and `plan-retro` apart. What it says:
   - **Invocations** (Quick start): `/session-retro <entry>` (the Claude Code sessions of a plan), `/session-retro session <session id>` (one Claude Code session with its subagents), and `/session-retro <start> <end>` (any window, two ISO 8601 times with a zone).
   - **Use instead**: `/plan-retro` for the findings of the refuter reports across plans; `/diagnose` for the cause of one failure; `/ordo-help` for which command comes next.
   - **What it reads**: `.agents/plan.yaml` (`ledger_root`, `archive_root`, `worktree_root`; a missing file or key is a refusal); for `<entry>`, the ledger folder under `<ledger_root>/` or `<archive_root>/` whose `plan.md` opens with `# Plan: <entry>` (none is a refusal); the transcript folders; the reader's output; for each proposal, the text it names; the earlier sessions reports under `<ledger_root>/retros/`, for the points already decided.
   - **Steps**, one action each, each ending on what is true when it is done; every step that can refuse comes before the first write:
     1. Resolve the window. `<entry>`: the start is the committer time of the commit that added the plan's `plan.md` under `<ledger_root>/<slug>/` (`git log --diff-filter=A --format=%cI -- <ledger_root>/<slug>/plan.md`), and the end is one second after the committer time of the latest commit that touches the folder under either root (`git log -1 --format=%cI -- <ledger_root>/<slug> <archive_root>/<slug>`), or the time of the run when the folder is still under `<ledger_root>/`. `session <id>`: no window; the reader's `--session` form. `<start> <end>`: as given.
     2. Find the transcript folders, under `$CLAUDE_CONFIG_DIR/projects` when that variable is set and under `~/.claude/projects` otherwise: the folder named, by the rule of "What is on the tree", after the repository's resolved path (`cd "$(git rev-parse --show-toplevel)" && pwd -P`), and every folder whose name starts with the name the same rule gives the resolved `<repository>/<worktree_root>/`. For `session <id>`, the one of those folders that holds `<id>.jsonl`. None found is a refusal that says Claude Code removes transcripts older than its `cleanupPeriodDays` setting.
     3. Make the run's working folder with `mktemp -d` under `$TMPDIR`, and run the reader over each folder with the window, each output and its stderr written into that folder. An exit 1 is a refusal that shows the `error: cannot read` lines; an exit 2 is a refusal that shows the reader's line; the outputs of all folders together holding no item is a refusal. The step is done when each output is on disk with its line and byte count.
     4. When the outputs together hold more than 1,000,000 bytes, stop ("Stops", "A large output") with the size and the number of parts; the user narrows the window with `/session-retro <start> <end>` or says to read it all.
     5. Choose the report's path, `<ledger_root>/retros/sessions-<YYYY-MM-DD>.md` with the date of the run, or, when that file exists, `sessions-<YYYY-MM-DD>-2.md`, then `-3`, and so on; write there, from `templates/sessions.md`, the window with what it was resolved from, the folders read with each output's line count and each `skipped` line, and the working folder's path. This is the first write, and every later step writes to this file.
     6. Read each output whole, in parts: a part is the line range an `awk` command over the output gives, at most 50,000 bytes, a line longer than that being a part of its own; a line the reading tool shows cut is printed in full with `sed -n '<n>p'` through `fold -w 2000`. After each part, the points it gave and the range read are written into the report, so after a compaction the next part is known and no point is lost. The step is done when every range of every output is recorded as read.
     7. Leave out a point whose places are all places of a point that has a decision in an earlier sessions report.
     8. For each point, write its places: each `<id> <line> <timestamp>` as the reader printed it, with the reader's line quoted (a long text cut at a sentence end and marked `...`).
     9. For each point, write its proposal, after reading the text it names. A change point names the rule (the rules file, a standards page, a rules file of the user's), the skill and its section, or the brief (the `spec` skill's `templates/brief.md`, or the brief of a step not yet landed), and gives the sentence to add, or the sentence as it stands beside the sentence it becomes, in the order `plan-retro`'s "The proposal for a recurring kind" gives (not written: add it; written where the Claude Code session did not read it: where it should be read; written and still broken: a sharper sentence or a change to the text that should have prevented it). A keep point names the text that produced the behaviour, or, when no text did, gives the sentence that would make it repeat. A proposed rule is in the voice of the page it goes into, with no date, incident or step number.
     10. For each proposal in turn, show it with its point and places and take the user's decision: approved, corrected (with the correction), or declined ("Stops", "The proposals"); the decision is written beside the proposal, in the user's words, before the next proposal is shown.
     11. Commit the report by its path, in one commit whose subject names the sessions report.
     12. Remove the working folder.
   - **Reference section** "The reader": the command form of Steps 3, with the reader named `templates/transcript_window.py`, and what its line prefix and its exit statuses mean.
   - **Stops**: "A large output" (Steps 4); "The proposals" (Steps 10: each proposal; resumed by the user's decision on it); the refusals: no configuration or a key missing; no such plan; no transcript folder; the reader's exit 1 or 2; no item in the window.
   - **Anti-patterns**: a point with no place; a quote taken from a `.jsonl` file (it skips the redaction; quote the reader's line); an output read in samples or its first part only (the points of the rest are lost; read every range); a proposal that loosens a rule or adds an exemption; an edit to a rule, skill or brief a proposal names (the change is made where the text is owned: an approved proposal goes into `/roadmap add` or a plan, or into the user's own rules files by the user).
   - **Rules**: every quoted line is a line the reader printed, with a secret the reader left in it written `<REDACTED>` and each character outside printable ASCII written as its code point `<U+XXXX>`; in the repository the skill writes only the sessions report.
2. `skills/session-retro/templates/sessions.md`, the sessions report's form: a title with the date; the window, how it was resolved (the entry and its two commits, the session id, or the two times), the folders read with each output's line count and skipped lines, the working folder, and the ranges read; `## Keep` and `## Change`, each point a `###` heading stating the behaviour, with `- Place:` lines, `- What happened:`, `- Proposal:` (the file and section, and the sentence to add, or the sentence as it stands and the sentence it becomes), and `- Decision:` (approved, corrected: ..., or declined); and a closing list of the approved proposals with the file each goes into.
