## What to build

### 1. Aliases from the configuration (ruling "Git aliases")

When a git command's subcommand is none of the checked ones and the inline configuration defines no alias of that name, the guard asks git for the aliases the configuration files define, and checks the expansion as it checks an inline alias.

The directory of the lookup:

- It starts at the event's `cwd` when the event holds `cwd` as a non-empty string naming an existing directory, and otherwise at the guard's own working directory.
- A `cd <word>` simple command earlier in the same command changes it for the simple commands after it, as the shell would.
  - Within a subshell `( ... )`, a `bash -c` or `sh -c` text, or a substitution, a `cd` holds only inside it.
  - The word is used when the lexer gives it as a literal: an absolute path, a path relative to the directory so far, or one starting `~` or `~/`, expanded from `HOME`.
  - A bare `cd` goes to `HOME`.
  - A `cd` whose word is not a literal (a variable, a substitution, `cd -`) leaves the directory unknown for the simple commands after it, and their lookups run from the directory before that `cd`; the docstring names this under "Not seen".
- A wrapper's directory option changes it for the command it wraps: `env -C <dir>`, `env --chdir=<dir>` and `--chdir <dir>`, `sudo -D <dir>` and `sudo --chdir=<dir>`.
- The command's own `-C <dir>` options change it next, in order, each relative to the directory so far, a leading `~` expanded from `HOME`.
- A directory that does not exist finds no alias.

The process:

- One process per lookup: `<git> [--git-dir=<d>] [--work-tree=<w>] config -z --get-regexp ^alias\.` run as a list of arguments, never through a shell, from the directory above.
  - `<git>` is the absolute path of `git` found on the guard's own `PATH` (`shutil.which`), found before any of the command's assignments apply; no `git` there finds no alias.
  - `--git-dir` and `--work-tree` are the command's own, in both spellings (`--git-dir <d>` and `--git-dir=<d>`), relative ones resolved against the directory.
- The process's environment is the guard's environment with `GIT_CONFIG` and every `GIT_TRACE` variable removed, plus the command's own assignments of only these variables: `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_COUNT` with its `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>`, `GIT_CONFIG_PARAMETERS`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `HOME`, `XDG_CONFIG_HOME`, `GIT_CEILING_DIRECTORIES`. No other assignment of the command reaches the process, so the guard never runs a program or writes a file the checked command names.
- Its standard error is captured and dropped; the guard prints nothing of it.
- Its output is decoded as UTF-8 with `errors="replace"`.
- All the lookups of one run of the guard share one time budget of 2 seconds: each process's time limit is what is left of it, and a lookup with nothing left finds no alias.
- A lookup is made at most once per directory, location options and environment in one run; the listing it returns serves every alias name looked up there.

What it finds:

- The alias of a name is the value of the last key in the listing whose part after `alias.` equals the name, compared without regard to case, as git compares it. The last key is the one git uses (the repository's over the global file's).
- A process that cannot start, runs past its limit, exits other than 0, or gives no matching key finds no alias; an empty value finds no alias. The command is then allowed, as input the script cannot read is allowed.
- A name that cannot be encoded for the process's arguments (a lone surrogate from the JSON) finds no alias, and the guard goes on to the next simple command without a traceback; its exceptions are caught by class (`OSError`, `subprocess.TimeoutExpired`, `UnicodeError`).
- An alias whose name, as typed, is a git command is never run by git, so the guard ignores it: only after a lookup has found an alias does the guard run `<git> --list-cmds=main,others` (same directory, environment and budget, made once per run and directory), and a name in that list, compared case-sensitively as git does, is no alias. A failure of that process counts as "not a command", and the alias is checked.

How the expansion is checked:

- Inline configuration wins over the files: an inline `alias.<name>` (from `-c`, `--config-env`, `GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>` or `GIT_CONFIG_PARAMETERS`) is used as today and no lookup runs for that name.
- An alias found in the files is checked exactly as an inline one: any alias but a `!` one as its words followed by the command's remaining arguments, looping, with the `seen` set ending an alias that names itself or a cycle. A name the loop reaches next is looked up inline first, then in the files.
- The location (directory, `--git-dir`, `--work-tree`) and the environment of the outer command stay in force for every lookup made while expanding it.
- A `!` alias is checked as shell text followed by the arguments git appends, carrying the inline configuration. Its commands start from the repository's top-level directory, as git runs them there, with the outer command's `--git-dir` and `--work-tree` as `GIT_DIR` and `GIT_WORK_TREE` and its assignments: the top-level is the location's work tree, from `git rev-parse --show-toplevel` in the same process budget, or the location's directory when that fails.
- The guard runs git only as this section says: the alias listing, the command list and the top-level, and only for a subcommand that is not checked and not an inline alias.

## Decisions taken in this brief (each reversible, none silent)

1. The lookup's directory follows the event's `cwd`, a literal `cd`, a wrapper's directory option and the command's `-C`, `--git-dir` and `--work-tree`, as section 1 says. The ruling says the lookup runs "in the command's directory (after `-C`)", and a literal `cd <dir> &&` before git is how an agent commonly names that directory; a directory given by a variable cannot be computed by the guard and is named under "Not seen". Running from the worktree's directory also reads a per-worktree `config.worktree`, since git reads it there.
2. The listing (`--get-regexp`) replaces one `--get` per name, since `--get` misses a subsection spelled in capitals and reads `GIT_CONFIG`, and one listing serves every name of a run.
3. The command-name check runs only after an alias is found, and uses `--list-cmds=main,others`, the programs git runs before an alias: the built-ins, git's exec path and the `git-<name>` programs on the PATH.
4. A lookup that fails or times out allows the command. The approved line of step 1 says input the script cannot read exits 0, and a guard that blocked every unknown subcommand when git is slow would block the plan skills' own commands. A command the guard checks directly (`git push`) is blocked whatever the lookups do.
