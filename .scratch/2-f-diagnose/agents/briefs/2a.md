## Cases

Code cases, each a test case in `person-driven.test.sh`. The script is run with its standard input from a file or a here-document, never a terminal. Beside each case stands the cost of a wrong answer, which is why it has a test.

- C1. An actions file of three lines and three lines of input: exit 0; the observations file holds exactly six lines, `Action 1: <text>`, `Observed: <line>` and so on in order, compared whole; standard output holds the text `Action <n> of 3: <text>` for each action, in order, and ends with the closing message. The same case is run once more with the script under `dash` when `dash` is installed. Cost: the record quotes a wrong run.
- C2. Blank lines, and lines of only spaces or tabs, between the actions: they are no actions; two real actions give `of 2` and four lines. Cost: a person asked to observe after an empty action.
- C3. An action and an observation holding `%s`, a backslash, `$HOME`, a backquote, a `*`, and spaces at both ends: each is written byte for byte in the observations file, the action is written byte for byte on standard output, and nothing is expanded or run. Cost: supplied text runs as a command, or the record misquotes it.
- C4. Paths with a space, for both the actions file and the observations file: exit 0 and the file written. Cost: the file written somewhere else.
- C5. Input that ends after the first of three observations: exit 1; standard error holds `person-driven: the input ended after observation 1 of 3`; the observations file holds the first pair, two lines, and nothing of action 2. Cost: what the person typed is lost.
- C6. Input that ends before the first observation (standard input from `/dev/null`): exit 1; `person-driven: the input ended after observation 0 of 1`; no observations file exists afterwards, so the same command runs again. Cost: the person's next run of the command shown is refused.
- C7. An empty observation line, then a line of spaces and tabs only, then a real one: the script prints `person-driven: type what you observed` to standard error after each of the first two and reads again; the file holds the real line for that action and one `Observed:` line. Cost: an observation that can show neither red nor green is quoted.
- C8. A last line of input with no newline at its end: it is the observation for its action and is written; exit 0. Cost: the last thing the person typed is lost.
- C9. The observations file already exists, as a regular file, as a folder, and as a symbolic link whose target does not exist: each exits 64 with `person-driven: the observations file <path> exists; name a new file`; the regular file's bytes are unchanged (compared with `cmp` against a copy) and the link's target is not created. Cost: an earlier run's observations overwritten, or a write outside the named file.
- C10. The actions file missing, a directory, or unreadable (`chmod 000`, skipped with a printed note when the test runs as root): exit 64, `person-driven: cannot read the actions file <path>`, and no observations file created. Cost: a run with no action quoted as a run.
- C11. An actions file with no action (empty, or blank lines only): exit 64, `person-driven: the actions file <path> holds no action`, and no observations file created. Cost: an empty file quoted as a run.
- C12. The folder of the observations file missing: exit 64, `person-driven: cannot write the observations file <path>`, and standard output holds no `Action` text. Cost: the person goes through every action and nothing is kept.
- C13. An append that fails during the run: the observations file's name is 300 characters long in a folder that exists and is writable, so the folder check passes and the first append fails. Exit 1 at that append, with `person-driven: cannot write the observations file <path>` on standard error, and standard output holds no `Action 2` text. Cost: the same as C12's.
- C14. An actions file whose last line has no newline at its end: that line is an action like the others. Cost: the last action is never shown.

Wrong numbers of arguments have no case: a wrong answer there costs nothing, as the change standard's "Scripts compute facts; judgment is read" weighs it.

Each code case has one mutation: one line of the finished script changed or removed, with which that case's test fails. On the unchanged tree the script does not exist, so every case fails there for that reason alone, and the mutation runs are the proof the change standard's rule 13 asks for in its fourth bullet. The report lists them in rule 13's table with four columns: the behaviour, the case, the mutation, and the `FAIL:` line the test printed with it.

Reading cases, checked by reading the unchanged tree and noted; the text after the change is judged by the reading of "Verify before you report" 6:

- R1. `skills/diagnose/SKILL.md` item 11 names no script file and no reference file.
- R2. The Stops row names no file and no command.

## Decisions taken in this brief (each reversible, none silent)

1. The command line, the form of the two files and the exit statuses are booked in `plan.md`'s Rulings, "Step 2a, the script's shapes": two arguments, since the ruling names a list given to the script and a file it writes; plain text written for a person to read; exit 64 for a refusal and 1 for a run that did not finish, the statuses `land.sh` uses.
2. Each pair is appended to the observations file as soon as its observation is read, both lines in one `printf`, so that input ending early or a signal loses nothing the user typed and leaves no half pair. The file is created by the first append.
3. An existing observations file is refused, never overwritten or appended to, since it may hold an earlier run's observations.
4. An observation that is empty or holds only spaces and tabs is asked for again, since it can show neither red nor green.
5. A line of the actions file that is empty or holds only spaces and tabs is no action, so the skill may space the list.
6. The script counts the actions before the first one is shown, to print `of <m>`. It counts nothing at the end: the change standard's rule 16 is met by checking the exit status of each append.
7. The script does not judge red or green. The skill reads the observations file and states which observation is the red.
8. The use of the script is stated in `references/person-driven.md` and not in a section of `SKILL.md`, since only a run whose symptom a person must trigger reads it.
9. "actions file" and "observations file" are descriptions defined in `references/person-driven.md`, not glossary terms: no other skill uses them. The glossary's **red command** entry stands, since a red command a person drives is still the one command that goes red on the exact symptom, and Steps 4 still states it.
10. Steps 4's three runs are kept for a red command a person drives; the reference file says each is one run of the script.

## What it must do

`person-driven.sh <actions file> <observations file>`:

1. With any number of arguments other than two, it prints `person-driven: usage: sh <the diagnose skill's folder>/templates/person-driven.sh <actions file> <observations file>` to standard error and exits 64.
2. It refuses, in this order, each with exit 64 and one line on standard error, before it prints an action or creates a file:
   - an actions file that is not a readable regular file: `person-driven: cannot read the actions file <path>`;
   - an actions file with no action: `person-driven: the actions file <path> holds no action`;
   - an observations path that exists as a file, a folder or a symbolic link, with or without a target (`-e` or `-L`): `person-driven: the observations file <path> exists; name a new file`;
   - an observations file whose folder does not exist or is not writable: `person-driven: cannot write the observations file <path>`.
3. An action is a line of the actions file that holds a character other than a space or a tab; a last line with no newline counts. The count `<m>` is the number of actions.
4. For each action, in order, numbered from 1, it prints `Action <n> of <m>: <text>` and a newline, then `What did you observe? (one line) ` with no newline, to standard output, and reads one line from standard input. Every line, of the actions file and of standard input, is read with `IFS= read -r`, so the spaces at its ends and its backslashes are kept. The actions file is read through a file descriptor of its own, so standard input stays the user's.
5. A line read that is empty or holds only spaces and tabs is answered with `person-driven: type what you observed` on standard error and another read, for the same action.
6. When the input ends with no character read for an action, it prints `person-driven: the input ended after observation <k> of <m>` to standard error and exits 1, `<k>` being the pairs already written. A last line with characters and no newline is an observation.
7. After each observation it appends the pair to the observations file in one `printf`: the lines `Action <n>: <text>` and `Observed: <line>`. Every text is an argument of a `%s`, never a format, and never passes through `eval` or an unquoted expansion. An append that fails prints `person-driven: cannot write the observations file <path>` to standard error and exits 1 at once.
8. After the last pair it prints a newline and `person-driven: wrote <m> of <m> actions, each with its observation, to the observations file <path>` to standard output and exits 0.
9. Each path reaches only a redirection or a `[` test, so a path that starts with a dash is a file name. A relative path is taken from the folder the script is started in.
10. Its head comment gives the usage, what it prints, what it reads and writes, every error line above and every exit status (0, 1, 64), as the change standard's rule 14 asks.

## Conventions

- POSIX `sh` with `set -u`; no bash form.
- ASCII only. Neither the script nor the test holds a literal tab: a tab is made with `printf '\t'`.
- No hard wraps in Markdown, no em dashes, no history in a comment.
- The test removes its scratch folder. A note for a skipped part (C10 as root, no `dash`) is printed before the last line, which is `PASS: person-driven.sh scratch tests`.
- The words "actions file" and "observations file" are the two names, used every time, in the script's messages, its head comment, the test and the reference file.
