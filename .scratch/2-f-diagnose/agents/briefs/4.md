## What to build

When the part is done, a diagnosis that has found its cause does not stop at the reported input. It names the operation that goes wrong, finds every other input that reaches that operation, runs each through the red command with and without the fix, and fixes and tests each one that fails the way the reported input fails, as part of the same defect. A run of the skill on the step-3 defect, following the text, ends with a fix that compares the folders themselves, handles a folder not yet made, and a test that covers each spelling and the link that failed.

### Names

1. **The new term.** The skill uses one new term, **other input** (of a diagnosis): an input other than the reported one that reaches the operation that goes wrong. Its entry is added to `skills/repo-setup/templates/plan-terms.md` after the entry **orchestrator**, and the same entry to `docs/glossary.md` after the entry **orchestrator**, word for word the same, in the form of the entries around it, with "Stated in: `diagnose`, Steps 15 to 19" (the steps it lands in).
2. **Words kept for what they mean.** "Probe" keeps its meaning, one change tied to one hypothesis: the run of an other input is called a run, never a probe. The run uses the red command with the other input in place of the reported one, so it drives the same code path and asserts the same symptom, and the glossary's **red command** stays true. The change being tested is named by what it is, the change of the probe that shows the cause, and no other new name is coined for it.

### `skills/diagnose/SKILL.md`, Steps 15 to 19 (lines 166 to 196), and `metadata.version`

3. **The cause at the operation.** Steps 15 states the cause at the operation that goes wrong: the comparison, the lookup, the write or the parse that gives the wrong result, with its place (file and line, or the section of a text), and the rule it breaks. A cause stated as a property of the reported input ("the path has two trailing slashes") is not stated at the operation; the text says so in its own words. When more than one probe turned the red command green, the cause is the hypothesis at the operation, and its probe is the one that shows it.
4. **A hypothesis is not falsified by one other input.** A hypothesis whose probe turned the red command green but broke an other input (as comparing resolved paths broke two folders not yet made) is not falsified: the broken input is recorded as an other input, and the fix at the operation is made to handle it. The text says this where Steps 15 states the cause.
5. **The other inputs.** After the cause is stated, the session lists each other input that reaches that operation, found by reading the code or text that produces the operation's inputs, from the shrunk case back to where the inputs come from:
   - another spelling of the same value (repeated or trailing separators, `.` parts, letter case, an encoding);
   - another name for the same thing (a link, an alias);
   - a value not yet there (a path not yet made, an empty value);
   - each other input the code that feeds the operation admits.
   The list holds what the code admits; it is not padded with inputs the code cannot produce. The reported input is not on the list.
6. **The runs before the fix.** Each other input is run through the red command, with that input in place of the reported one, on the tree without the fix and on the tree with the change of the probe that shows the cause. Each result is recorded, and each other input is put in one of three classes, named the same way in the skill and in the record:
   - part of the defect: red on the tree without the fix, with the reported symptom, whether the probe's change turns it green or not;
   - not part of the defect: green on the tree without the fix;
   - another defect: wrong on the tree without the fix with another symptom, at another operation.
   Each input that is part of the defect fails the way the reported input fails, so its failure costs what the defect's costs; the change standard's case rule ("A script handles a case only when that case has happened or when a wrong answer on it costs something") holds for it, and the text may say so in one clause.
7. **The test.** Steps 16's test reproduces the shrunk case and each other input that is part of the defect, one case each, whether or not the probe's change already turned it green, so a later fix that narrows again goes red. Steps 17 runs it on the tree without the fix and quotes the failure of each case.
8. **The fix.** Steps 18 makes one change at the operation that is right for the reported input and every input part of the defect, and leaves every input not part of the defect as it was on the tree without the fix. It is never one change per spelling. When the probe's change leaves an input of the defect red, or breaks an input that was green, the fix is changed once more at the operation; an input still wrong after that second change is written in the record as not fixed, with its result, and the Cause section and the session's final message say the fix does not cover it. The anti-pattern row "A guard for a fix" still holds.
9. **The runs after the fix.** Steps 19 runs the test, the red command, the original unshrunk case and the red command on every other input listed, each quoted in the record: each input part of the defect is green, each input not part of the defect gives what it gave on the tree without the fix, and each input of another defect is left out of the result.
10. **Another defect.** An input of another defect is named in the record's new section with its result, and the fix does not reach for it. The skill adds nothing else for it: the record is read where it is kept (by the user outside a plan, by the orchestrator inside one), so no step of `diagnose` beyond 15 to 19 changes for it.
11. **A defect in text.** For a defect in a skill, a page, a rule or a brief, the operation is the instruction that led to the wrong behaviour, and the other inputs are the other situations that instruction governs. Each is read against the text before and after the fix and quoted; no test is written, as Steps 16 already says for text.
12. **Who is present.** The new work adds no stop and no wait: run by a person or by a diagnosis agent, it goes on without a reply, as Steps 15 to 19 do now.
13. **Numbering.** No step of `diagnose` is added, removed or renumbered: the new text goes into Steps 15 to 19 as bullets, since other skills and the glossary name `diagnose` steps by number. The Done line of each changed step says what is done with the new work in it.
14. **Version.** `metadata.version` goes from "2.0.0" to "2.1.0": 2.0.0 is in the released tags, and the skill does something it did not do while every run that worked before still works (`docs/dev/skill-layout.md`, the minor part).
