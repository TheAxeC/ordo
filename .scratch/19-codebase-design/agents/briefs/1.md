### The standards pages and the search order

The skill names five subjects of standards page: the change standard, the design principles, the coding standards (a common page and one page per language), the UI standard and the prose standard. It finds a repository's pages of each subject in this order, and no place of the order refuses a repository:

1. the pages the repository's `plan.yaml` names under `rules` and `standards`, when the repository has one, found as `/plan`'s "What it reads" 1 finds it;
2. the fixed names under `docs/dev/` that `repo-setup`'s "The tree" gives each subject;
3. the default pages, `templates/docs/dev/` in the `repo-setup` skill's folder, which stands beside this skill's folder.

Place 1 reads the first `plan.yaml` found in `.scratch/`, `docs/` and `.agents/` at the repository root, in that order, each path read relative to the folder that holds the file. In the `projects:` form it reads the `rules` and `standards` of every project.

A subject is present in a repository when a page found at place 1 or 2 holds rules of that subject, wherever they stand, such as a section of another page. Which subject a page or a section holds is judged by reading it. The `repo-setup` folder missing beside the skill's folder is a refusal that names the folder, in both modes.

### The call with no mode

`/codebase-design` with no mode gives the vocabulary for work that designs or changes a module, as the source's `codebase-design` does: the session reads `references/vocabulary.md` and uses its terms and principles in that work, with `references/deepening.md` for a cluster's dependencies and `references/design-it-twice.md` when the user wants other interfaces. It writes no file.

### The mode `standards`

`/codebase-design standards` fills the standards pages of the repository it runs in. It adds and rewrites nothing that exists.

- It finds the repository's pages by the search order, the languages of the repository from the file extensions as `repo-setup`'s "What it reads" names them, and whether the repository has a user interface: a repository that uses Svelte or SvelteKit has one, and otherwise the user is asked once.
- For each rule of each default page of a subject that applies (the UI standard only with a user interface, a language page only for a language the repository has), it looks for the same rule in the repository's pages. A rule that already stands there is left as written.
- A rule that is missing is drafted in the concrete form it takes in that repository, read from the code: each placeholder of the default page filled from what the code shows, and the check that enforces the rule named where the repository has one. A placeholder the code does not settle is put to the user as a question in the draft.
- A drafted rule goes where the repository keeps that subject of rule. A subject the repository lacks gets a new page, beside the pages the repository already has, and under `docs/dev/` when it has none (D14).
- The prose standard is copied as it is when the repository has none, and left alone when it has one.
- A new page is added to the `standards` list of the repository's `plan.yaml` when it has one, as part of the draft.
- The whole draft is shown before anything is written: each addition with the file and the place it goes to, each new page whole, each change to `plan.yaml`, and each default rule found already present with where it stands. That is the skill's stop "The draft".
- On the user's approval or correction the additions are written, and the skill names every file it wrote. It makes no commit.

### The mode `review`

`/codebase-design review [area]` reads the code against the standards pages and writes candidates. The area is optional.

- Scope first, as the source's "1. Explore" says: an area the user names is taken; otherwise the commit history shows the files and areas that keep changing, and those are read first; with no clear area the whole repository is read.
- It reads the repository's glossary and its ADRs in the area before the scan: the glossary and the `adr` folder the repository's `plan.yaml` names when it has one, and otherwise `docs/glossary.md` and `docs/adr/` when they exist. With neither, the skill still runs.
- It finds the pages by the search order. For a subject the repository lacks, the code is held to the default page of that subject: each candidate under such a rule says that the rule comes from the default page, and a sentence of the default page that still holds a placeholder is skipped (D12). The report names each subject the repository lacks and `/codebase-design standards` as the way to fill it.
- It starts one fresh agent that changes nothing to walk the code. The agent is given the pages, `references/vocabulary.md`, the scope and the source's questions of "1. Explore" on where understanding is hard, with the deletion test. It returns candidates.
- Each candidate names the standards page and the rule it breaks, its files and lines, the problem, the fix, the benefit and how strongly it is recommended: `Strong`, `Worth exploring` or `Speculative`. The benefit is given in terms of locality and leverage and of how the tests would improve. The text uses the repository's glossary for the domain and the terms of `references/vocabulary.md` for the design, as the source asks.
- The session reads the files and lines of each candidate before the report is written. A candidate whose lines do not show what it says is dropped.
- A candidate that contradicts an ADR of the repository is shown only when the friction warrants reopening that ADR, and is marked as the source's "ADR conflicts" says.
- The report is one HTML file as `references/report.md` gives it, written to the operating system's temporary folder as the source says, so that nothing lands in the repository, opened for the user, and its absolute path given. It ends with the top recommendation. No interface is proposed yet.
- The stop "The candidates": the user is asked which candidate to explore.
- For the picked candidate, when the user wants to see other interfaces, the session follows `references/design-it-twice.md`, and classifies the dependencies as `references/deepening.md` says.
- The picked candidate then becomes a roadmap entry (D5): the session invokes `/roadmap add` with the candidate as the goal, which has its own approval, and then `/grill` on that entry, which settles its decisions, its glossary terms and its ADRs. In a repository with no plan configuration, the session first invokes `/ordo-init`, which has its own draft and approval, and then goes on with `/roadmap add` and `/grill`; when the user declines `/ordo-init`, the skill ends with the report as its result and says that no roadmap entry was written.
- A candidate the user rejects for a reason a later review would need is offered as an ADR, as the source's third bullet of "3. Grilling loop" says. On the user's yes the record is written in the repository's ADR folder, from its `template.md` or, with none, in the form of its latest record, with status `proposed` and numbered after the folder's highest. A repository with no ADR folder gets one first, from the `repo-setup` skill's `templates/docs/adr/README.md` and `template.md`.

## Cases

Each is checked by reading the skill's text; the first read is of the unchanged tree, where the skill does not exist.

- A repository whose `plan.yaml` lists its pages in another folder than `docs/dev/`: both modes read those pages, and `review` uses no default page for a subject those pages hold.

- A repository with no `plan.yaml` and no standards page: `standards` drafts every page that applies under `docs/dev/`; `review` runs, holds the code to the default pages, and says in each candidate that its rule comes from a default page.
- A repository whose coding-standards page holds its design principles as a section: `standards` treats the design principles as present, leaves that section as written, and drafts only the default rules the section lacks, into that section's page.
- A default sentence that still holds a placeholder, in `review`: no candidate cites it.
- A repository without a user interface: no UI standard is drafted, and no candidate cites one.
- `review` in a repository with no plan configuration: the report is written and opened; at the pick the session invokes `/ordo-init`, and after its approval `/roadmap add` and `/grill`.
- The `repo-setup` folder missing beside the skill's folder: a refusal that names it, before anything is drafted.
- `standards` on a repository where every default rule is already present: the draft says so, and nothing is written.
- The report file opened with no network: it shows every card and picture, since `references/report.md` names no address to load from.
- The frontmatter: `name` equals the folder's name and `description` is at most 1,024 characters.
- A shipped file names nothing private: no file this step writes under `skills/` or in `README.md` names a repository, a person, a project or a path of the author's own.
