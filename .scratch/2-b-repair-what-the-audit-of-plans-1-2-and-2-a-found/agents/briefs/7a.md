## What to build

The rulings of this plan (`plan.md`, Rulings, open items R and S) fix the shape:

1. **The key.** `worker_allow:` is a new optional key of `.agents/plan.yaml` and of the ledger's configuration block: a list of command prefixes a builder started from a shell may run, default `[]`. `[]` means the list is built from the plan's verify list and the step brief's own check commands.
2. **`skills/plan-orchestration/templates/allow_list.py`**, new: `allow_list.py <state file> [<command>]...` prints the step's allow list, one prefix per line. When the configuration block's `worker_allow` is a non-empty list it prints those entries, in order. Otherwise it takes each command of the block's `verify:` list and each `<command>` argument, splits it into its simple commands at `|`, `||`, `&&` and `;` (outside quotes), removes each redirection (`2>&1`, `>file`, `>>file`, `<file`, `2>/dev/null`), and prints each simple command that remains, stripped, once, in the order first seen. It exits 64 on a usage error, a state file that cannot be read, no first `yaml` block or one that is not valid YAML, a `worker_allow` that is not a list of non-empty one-line strings, and an empty result; 0 otherwise. Its test `allow_list.test.sh` runs on scratch state files.
3. **`launch.sh`**: a new option `--allow-file <file>`, required in claude mode and refused in codex mode and transcript mode (exit 64 with usage). The file holds one command prefix per line. It is made absolute like the other path options, carried through both re-runs of the body, and read when the builder starts: each non-empty line becomes `--allowedTools "Bash(<line>:*)"` on the `claude` command line. A missing or unreadable file, or one with no non-empty line, is a usage error, exit 64, before anything starts. The header comment and the usage text say it. The codex recipe is unchanged: its sandbox confines the builder.
4. **`launch.test.sh`**: the claude stub logs its arguments already; the cases below check the `--allowedTools` arguments it receives, first launch and resume, and each refusal.
5. **`check_config.py`** and its test: `worker_allow` is known with its default `[]` through `templates/plan.yaml`; a value that is not a list, or holds an entry that is not a non-empty one-line string, is an error naming the key and the value; the docstring says so.
6. **The templates**: `worker_allow: []` in `templates/plan.yaml` after `launch_note`, with the comment `# optional, default []. Command prefixes a builder started from a shell may run (the plan-orchestration skill's templates/allow_list.py); [] means the verify list and the brief's check commands.`; the same key in each project block of `templates/plan.projects.yaml`; `worker_allow: []` in the configuration block of `templates/orchestrator-state.md` with its comment.
7. **The recipe text**, `skills/plan-orchestration/SKILL.md`, "Launching a builder": the claude code block gains `--allow-file <allow file>`; a shell launch's item 1 writes the allow file (from `python3 <this skill's folder>/templates/allow_list.py <state file> <each check command of the brief>`) and names it in the dispatch block as `allow_file`; the dispatch field list in `templates/orchestrator-state.md` line 27 gains `allow_file`.
8. **The pages**: `README.md:96` says what `worker_allow` holds and its default; `skills/ordo-init/SKILL.md` item 7 says `worker_allow` is left out unless the repository names commands beyond the verify list; the new test is added to `README.md` Tests, `docs/dev/building.md` and the command block of `docs/dev/change-standard.md`, after `launch.test.sh`.

## Cases

- `allow_list.py` on a state file with `verify: ["sh a.test.sh 2>&1 | tail -1", "python3 utils/x.py"]` and no `worker_allow` prints `sh a.test.sh`, `tail -1`, `python3 utils/x.py`, exit 0.
- The same with the extra argument `sh b.test.sh 2>&1 | tail -1` prints `sh a.test.sh`, `tail -1`, `python3 utils/x.py`, `sh b.test.sh`: `tail -1` once.
- `git ls-files -coz --exclude-standard | xargs -0 perl -CSD -ne 'print if /a|b/'` gives `git ls-files -coz --exclude-standard` and `xargs -0 perl -CSD -ne 'print if /a|b/'`: the `|` inside quotes does not split.
- `a && b; c || d` gives `a`, `b`, `c`, `d`.
- `worker_allow: ["sh only.sh"]` with a verify list prints `sh only.sh` alone.
- `worker_allow: "sh only.sh"` (a string), `worker_allow: [""]`, `worker_allow: ["a\nb"]`: exit 64, the message names `worker_allow`.
- `worker_allow: []` with an empty verify list and no argument: exit 64, the message says the list is empty.
- A state file with no `yaml` block, or a missing state file: exit 64.
- `launch.sh claude ... --allow-file <file holding "sh a.sh" and "tail -1">`: the stub receives `--allowedTools Bash(sh a.sh:*) --allowedTools Bash(tail -1:*)`, on a first launch and on `--resume`, from a path holding a space.
- `launch.sh claude` without `--allow-file`: exit 64, usage printed, nothing started (no pid file written).
- `--allow-file` naming a missing file, or a file of blank lines: exit 64, nothing started.
- `launch.sh codex ... --allow-file <file>`: exit 64, "--allow-file is for claude only".
- `launch.sh transcript ... --allow-file <file>`: exit 64.
- `check_config.py` on a plan.yaml with `worker_allow: sh a.sh`: an error naming `worker_allow` and the value; with `worker_allow: [sh a.sh]`: no error; without the key: the note `worker_allow not set, default [] applies`.

The builder's first task, before any code changes: turn every case above into a test of the step, run the tests against the unchanged tree, and note each case's result. No prototype script stands in for the tests.

When the first run finds a case the brief's own rules get wrong, the builder stops there, before changing any code, and hands back the first run and that case, with the rule and the result it gives. The orchestrator rules on the case and resumes the builder with the ruling, and the final report carries it.

## Decisions taken in this brief (each reversible, none silent)

1. The list reaches `launch.sh` as a file (`--allow-file`, one prefix per line) rather than a repeated option, so it passes through the body's two re-runs as one path and is recorded in the dispatch block.
2. The default list is built by a script beside `launch.sh`, `allow_list.py`, so the orchestrator and a person running the recipe by hand build the same list.
3. `--allow-file` is required for a claude launch: without it the builder can run no command, which the step exists to end.
4. A prefix is passed as `Bash(<prefix>:*)`, so each listed command runs with any further arguments, as ruling S states.
