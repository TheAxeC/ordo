## What to build

1. **An exit file after every KILL once the builder has started.** When the builder ends while the leader lives, the builder's runner leaves behind, before it exits, a guard process that holds the builder's code. The guard waits until the leader is gone. It then writes the exit file with that code when none is present, and removes a `<exit file>.tmp` the leader left. It never writes over an exit file present. When the leader finishes normally, the guard finds the exit file and writes nothing. The guard ignores TERM, INT and HUP, so the leader's own stops do not end it before the leader is gone, and it ends within about a second of the leader.
2. **No stale exit file after a relaunch.** The session leader, the builder's runner and the guard hold the launch's lock descriptor for as long as each lives; the builder and the note calls do not inherit it. A launch of the same pid file while any of them lives is refused with exit 75, naming the lock, before it removes anything. So a killed run's runner or guard can no longer write after a later launch removed the file.
3. **A bounded stop.** `session_members` reads the scanner's answer with a time limit of two seconds. Past it, the runner stops the scanner and goes on with the processes `descendants` finds, so a stop always ends.
4. **One writer's temporary name each.** The leader, the runner and the guard each write their own temporary file beside the exit file (the writer's pid in its name), so two writers never share one. The launch removes an exit file and the temporary files an earlier run left.
5. **The texts made true.** The head comment of `launch.sh` (the "Exit file" paragraph and the runner's and `$detach`'s comments), `skills/plan-orchestration/SKILL.md` lines 182, 191-193 and 210, and `templates/launch-note.md` lines 27-30 say what the code does: which stops leave an exit file (every stop once the builder has started), which leave none (a KILL while the note's `start` runs, before any builder started), and that a relaunch waits while a killed run's runner or guard lives.

## Decisions taken in this brief (each reversible, none silent)

1. The guard is started by the builder's runner, before the runner exits, so no moment exists between the builder's end and the guard's start. It watches the leader by its pid with `kill 0`, since its parent is the runner, which exits.
2. The relaunch is kept safe by the lock rather than by reading the pid file before each write, since the lock is released by the system only when its last holder ends, with no window between a check and a write.
3. The order of the note's `end` and the exit file is unchanged: when the leader lives, `end` is called first and the exit file written after it, as `templates/launch-note.md` gives it to a note command.
4. The scanner's time limit is two seconds, inside the land skill's five-second wait.

## Cases

Each is a case of `launch.test.sh`. Each window is widened in a patched copy where it is too short to hit, as the file already does. Each case names the revert that turns it red.

- The builder exits 0 while the note's `end` hangs; KILL to the leader alone: within five seconds of the KILL (`land_wait`), the exit file says `exit 0`, and no process of the session and no guard is left.
- The builder exits 3; KILL to the leader between its temporary write and its move (a `sleep` put between them in a patched copy): the exit file says `exit 3`, and no temporary file is left.
- The builder exits 0 and the launch ends normally: the exit file says `exit 0`, written once, the note's `end` called before it (the order the stub logs), and no guard left once the leader is gone.
- KILL to the leader while the builder, ignoring TERM, is being stopped; at once a second launch of the same pid file: refused with exit 75 naming the lock, while the killed run's runner lives; once the killed run's processes are gone, a launch runs and its exit file is its own builder's code, never `exit 137`.

Two further cases each turn red when one guard of the no-replace write is reverted alone: the `-e` return, and the `link` (replaced by `rename`), each with the window that reaches it widened in a patched copy.
- A scanner that never answers (a patched copy whose scanner sleeps): TERM to the leader, then KILL two seconds later, as the land skill does: within five seconds the exit file is present and no process of the builder is left.

## What it must do

- Every stop of a started builder leaves an exit file within five seconds of a KILL: a KILL while the builder runs (the runner, `exit 137`), a KILL after the builder ended (the guard, the builder's code), a KILL during the leader's write (the guard). The only stop that leaves none is a KILL while the note's `start` runs, before any builder started.
- A relaunch never reads an exit file a killed run wrote after the relaunch removed it.
- The builder's process tree does not hold the lock, and a note call does not hold it.
- A stop never waits on the scanner for more than two seconds.
- Under load: the whole of `launch.test.sh` run 32 times at 16 at once under `sh` and under `LAUNCH_SHELL=dash`, each with 0 red, the counts in the report.
