## What to build

1. **The search order.** A skill that reads the plan configuration finds `plan.yaml` in this order and uses the first file found: the folder named in the call, then `.scratch/plan.yaml`, `docs/plan.yaml` and `.agents/plan.yaml` at the repository root. With no file found, the refusal each skill has today for a missing configuration is raised, and it names the places looked in. The order is stated in full once, in the `plan` skill's "What it reads" 1, and every other skill that reads the configuration says that it finds the file as `/plan` does, as each says today that the keys are read as `/plan` states them.
2. **The folder in a call.** A call names the folder in front of the entry, where a project name goes today: `/plan apps/web/12`, `/spec apps/web/12 2`, and the same for `/grill`, `/refute`, `/land`, `/diagnose`, `/ordo-help`, `/roadmap`, `/plan-orchestration` and every other call that takes an entry or a project. The folder is a path from the repository root. Each skill's Quick start, its "What it reads" and its Stops say so.
3. **Paths in a `plan.yaml`.** Every path a key of `plan.yaml` holds is read relative to the folder that holds the file: `roadmap`, `verification`, `rules`, `ledger_root`, `archive_root`, `worktree_root`, `worktree_paths`, each entry of `standards` and `adr`. `look`, `bench` and `design_references` hold text and are not resolved. A key left out takes its default as the example file states it, read from the repository root: `adr` is then `docs/adr` at the repository root, wherever the file stands. The file's folder and the repository root are resolved through links before a path is resolved or compared. A path may lead out of the file's folder through `..`; it is refused when, resolved, it lies outside the repository. A `ledger_root` of `.` in `.scratch/plan.yaml` is the folder `.scratch`; only the repository root itself is refused as a ledger root or a worktree root. The configuration block `/plan` writes into a state file holds each path as it reads from the repository root, so the briefs, `checks.sh` and every skill that reads the block read it as today.
4. **`worktree_root`.** The key is optional. A `plan.yaml` that does not name it, a project of the `projects:` form included, uses `.agents/worktrees` at the repository root, wherever the file stands. The example files, the keys `check_config.py` treats as required, its note for an optional key left out and each skill's text follow.
5. **`check_config.py`.** `check_config.py <path of plan.yaml>` checks the file at that path and opens no other configuration. The repository root is the top level of the git repository that holds the file. Every check it makes today is kept, each path resolved as item 3 says: the pages exist, git ignores the worktree root (the default of item 4 when the key is left out), git does not ignore the configuration file, `adr` resolves to a folder inside the repository. Every line it prints names the file by its path from the repository root. Called with no argument, with a path that is no file, or with a file in no git repository, it prints an `error:` line and exits 1. The path may be absolute or relative to the current folder. `check_config.py --find <repository root> [<folder>]` prints the path, from the repository root, of the first `plan.yaml` in the order of item 1 and exits 0, or prints an `error:` line that names the places looked in and exits 1. The folder is a path from the repository root, with or without a trailing slash; a folder that resolves outside the repository is refused; it is the one executable statement of the order, which `ordo-init` and `repo-setup` run before the check. The head comment states both forms.
6. **`land.sh`.** `land.sh <state file> <slug>-<step> <base> <path of plan.yaml>`: the fourth argument is required, and the script opens that file and no other. A missing fourth argument, or one that is no file, is refused with exit 64 before anything is touched. `ledger_root` and `worktree_root` are read relative to the file's folder; `worktree_root` left out is `.agents/worktrees` at the repository root; each resolved folder must lie inside the repository and not be its root. The path is relative to the repository root or absolute, as the state file's is. Each refusal names the file by the path given. The head comment, the `land` skill's "The landing script" and its Steps say how the script is run.
7. **Ordo's configuration.** `.agents/plan.yaml` moves to `docs/plan.yaml` with `mv`, each path rewritten relative to `docs/`: `roadmap: roadmap.md`, `verification: dev/building.md`, `rules: dev/change-standard.md`, `ledger_root: ../.scratch`, `archive_root: ../.scratch/archive`, `worktree_root: ../.agents/worktrees`, `standards: [dev/skill-layout.md, ../skills/repo-setup/templates/docs/dev/prose-standard.md, glossary.md]`. Its head comment says that every path is relative to the file's folder. No other value changes, and the file gains no key. `.gitignore` loses the line `!.agents/plan.yaml`, and its comment says what the remaining line ignores.
8. **A new configuration.** `ordo-init` and `repo-setup` write a new configuration to `docs/plan.yaml`, and the README's setup text says the same. The two example files are written for that place: their head comment says to copy the file to `docs/plan.yaml` and that every path is relative to the file's folder, and their values read from `docs/` (`roadmap: roadmap.md`, `ledger_root: ../.scratch`, `archive_root: ../.scratch/archive`, a project's pages the same way). `ordo-init`'s draft follows the same rule, and its text on the ignore rules and `skills/repo-setup/templates/gitignore/common.gitignore` no longer keep `.agents/plan.yaml` tracked. `ordo-init`, run on a repository that has a configuration, checks the file the search finds. 9. **Every place that names `.agents/plan.yaml`.** Each of the 161 lines is read. A line that tells a skill, a script or a person where the configuration is states the search order, points at the place that states it, or names the file as found ("the `plan.yaml` found", "the plan configuration"); a line keeps the name only where it states the place `.agents/plan.yaml` as one of the four of the order, or builds that place in a test. ## Decisions taken in this brief (each reversible, none silent)

1. A folder and a project name share the place in front of the entry. The longest leading part of what stands there that is a folder holding a `plan.yaml` is the folder; what is left before the entry names a project of that file's `projects:` form. With no such folder the file is found in the three places at the root, and the whole part names a project, as today. Five calls read by this rule, on a repository with `apps/web/plan.yaml` (one project), `tools/plan.yaml` (projects `a` and `b`) and `docs/plan.yaml` (projects `x` and `y`):
   - `/plan 12`: `docs/plan.yaml`, refused as today since the `projects:` form needs a project.
   - `/plan x/12`: `docs/plan.yaml`, project `x`, entry 12.
   - `/plan apps/web/12`: `apps/web/plan.yaml`, entry 12.
   - `/plan tools/a/12`: `tools/plan.yaml`, project `a`, entry 12.
   - `/spec apps/web/12 2`: `apps/web/plan.yaml`, entry 12, step 2.
2. A call with no folder, `/plan-orchestration` with no entry among them, reads the file found in the three places at the root; the plans of a `plan.yaml` in a project folder are run by naming the folder, and the count of steps in flight is made over the open plans of the file the call found.
3. `ordo-init` and `repo-setup` write a new configuration to `docs/plan.yaml`, where Ordo's own then stands, and the example files are written for that place (item 8).
4. `check_config.py --find` is the executable form of the search order, so the six cases of the gate have something to run.
5. The path of `plan.yaml` is `land.sh`'s fourth argument, after the three it has.
6. Ordo's `docs/plan.yaml` keeps a `worktree_root` line, rewritten as `../.agents/worktrees`.
7. A default of a path key is read from the repository root, as the default of `worktree_root` is.
