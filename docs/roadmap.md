# Roadmap

What is open, in the order it is built, what is not yet specified, and what is done. An entry of the open order is one piece of work `/plan` can open: its goal, its gate (the check that proves it done) and what it waits on. The order is dependency order: an entry comes after everything it waits on. Entry numbers never change once written; an entry placed between two others takes the number of the one before it with a letter (`3.A`), and an entry that moves in from "Not yet specified" keeps its number.

The section "Not yet specified" holds work whose gate cannot yet be named, each entry with its goal and what must be known before its gate can be named. `/plan` refuses such an entry until `/roadmap add <entry>` names its gate and places it in the open order.

An entry that rebuilds or answers an existing skill follows that skill's design: its agents, phases, cycles and stops are kept, and a deviation is made only with its reason and your ruling.

Status: `[ ]` open, `[~]` in progress, `[x]` done (its gate ran and passed, with the output beside it).

## 13. researcher

- Status: [ ]
- Goal: The researcher skill, with seven modes. `novelty` is a light check made by the session itself, with no agent started: it states the claims of an idea, searches for the closest prior work on each, and writes one page with the nearest works and their references, what each already does, what the idea adds beyond them and a verdict per claim (new, partly done or done), each cited work confirmed with `paper`'s `lookup.py`; the page is given to `paper` as a starting point and replaces none of its literature search. `idea` takes a rough sketch to research questions and claims: it works in rounds, each choice of the idea put with its options and a recommendation, runs `novelty` on each candidate claim between rounds, and writes the questions and claims into the project's `README.md`. `integrity` runs the integrity check, of the references and of the claims against each source's full text, of the numbers against the saved runs and of the figures against their traces, and the ethics check, on a finished draft. `manuscript` runs `paper`, the integrity and ethics checks, the review of `paper-review-panel`, the revision, the re-review and the final check, in the order academic-pipeline gives its stages from the writing on. The integrity check's corrections and its records sent to `paper` keep file names, script names, paths, code identifiers, job, run or exit-code language and software-operations wording out of the manuscript text, a fact from code or a log written as the scientific claim it supports. The `integrity` and `manuscript` modes are a copy of academic-pipeline's files (`research-hub/.agents/skills/academic-pipeline/`), each under its own folder and name, with the documents those files rely on taken from the same version of its public repository, changed only where a ruling of yours in the plan's Rulings says so, each with its reason; the ethics check is built from the page `paper` held for it. A file `NOTICE.md` at the repository root names the skills adapted from that repository, its author and its licence. The `research` mode of `researcher`, which takes an idea to results: the session directs the work through six named stages (Frame, Build, Baseline, Experiments, Compare, Consolidate), each with a completion criterion, and a stage can send the work back to itself or to an earlier one; each piece of code is built by a fresh agent from a written brief and read by a fresh reviewer before any job is submitted. Frame sets the question, the baseline, the metric, the limits on storage and compute, and the dataset, chosen from candidates shown with their size, licence and fit to the limits. Experiments holds one campaign or several, each with its own method. It runs the experiments, SLURM jobs among them, and when a result does not beat the baseline it diagnoses why (the dataset, the method, the implementation or the question) and proposes a new method, a change of the method or another dataset, never writing up a negative result; it stops after each such result or goes on by itself for a number of methods you set. It states where a project's code, results, logs and drafts live, in a default layout whose entry file is the project's `README.md`, with dead ends kept runnable in `code/attic/`, and one project can hold several manuscripts. An adopt mode reads a project already underway and continues from the first stage not done, counting partial or inadequate results as not done. The `full` mode runs `idea`, then `research` and `manuscript`, shows the modes it will run and the ones it leaves out, as for a review paper or for results that exist, each with its reason, and goes on after you confirm. The `revision` mode takes a paper of the project and its referee comments: each comment that asks for new experiments, a new analysis, another dataset or another baseline is run as a campaign of the project's `research` stages, and then `paper`'s revision runs with the new results, the response letter, the integrity check and the re-review, as `manuscript` runs them; no result that does not beat the baseline is written up as a finding. The `research` mode holds a project to four rules: one documented command rebuilds every reported number, table and figure from the raw inputs, and names each missing prerequisite at its start; nothing computes on a cluster's login node, and every job goes through the scheduler; an idea is not shelved after a weak first attempt; and the project's notes let a new session resume without the conversation. At the end of the entry, `ordo-help` covers everything Ordo offers: the academic skills and the code skills beside the plan skills, each with what it is for and the command that starts it, and from a sentence on what you want to do it names the skill, the mode and the command.
- Gate: one `novelty` run on an idea you name, its page read by you, each work it cites confirmed by a record that `lookup.py resolve` prints for it with a title ratio of 0.70 or above and no `DOI_MISMATCH`; `diff -r` of the folders of the `integrity` and `manuscript` modes against `research-hub/.agents/skills/academic-pipeline/` and of the documents taken from its public repository against those documents, prints only differences the plan's Rulings name, read once by a fresh agent that lists each difference with the ruling that covers it, or none, and read by you; the text of the `idea` mode, of the `research` mode, of its adopt mode, of the `full` mode and of the `revision` mode read by you; a fresh agent reads the skill once and lists, for each sentence of the goal on these five modes and for each of the four rules, the step of the skill that carries it, or "none", and the list holds no "none", read by you; one run of `/ordo-help skills` whose output names every skill folder under `skills/`, each with what it is for, checked by reading the output against `ls skills/*/`, and one run of `/ordo-help` with a sentence on what you want to do that you name, both read by you; the verify list of `docs/dev/building.md` passes on main.
- Waits on: 6, for the review its `manuscript` mode calls; 19 and 25, so that the `ordo-help` change covers every skill and mode built before it.
